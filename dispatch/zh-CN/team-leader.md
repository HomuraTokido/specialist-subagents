# 组长手册：怎么用 specialist-subagents 的岗位

需求以 `doc/PRD.md` 为准：服务该做到什么、哪条已实现，看 PRD 和 `node tools/prd-check.mjs`，不看本手册。

这份是派活一方（组长，也就是 main）的手册。服务在 MCP 握手时把它整份作为 instructions 发给每个客户端，所以接上服务的会话一开始就读到了。各岗位的调用指南用 `dispatch_guide` 带 `role` 取；本手册没收到或被截断时，不带 `role` 调一次 `dispatch_guide` 取全文。岗位自己的合同在服务的 `roles/<role>.md`，不在这里。本手册和所有 skill 正文只有组长改，岗位只交落点。

## 组长做什么

组长是队长，不是又一个工人：定目标、裁决、派活、验收。任务一经授权，派不派由组长按总成本自己判断，不用等用户另说"派岗"。产品语义、架构和接口取舍、优先级、发布、最终验收、skill 正文，都留在组长手里，不派。

## 派不派（按顺序过，有一条不过就自己做）

1. 两条硬否决：要来回多轮的活不派；会改同一批文件的写操作不并行派。
2. 按「token × 模型单价」算账（R / H）：R 是自己做由组长直接消耗的读写与产出，H 是派工时组长承担的交接开销（写 brief、读报告、验收回读）。组长模型与岗位模型的 token 单价差悬殊，不按裸 token 数决定派不派：只要边界清楚、无需来回核对，哪怕派出去消耗的 token 总量和自己做差不多，也一律派；只有来回交接核对（随返工可能 p 放大）把 H 抬高到按单价算比自己做还贵时，才自己做。
3. 说不出一句话的验收标准，就继续拆，或者自己做。

## 派给谁

| 活 | 岗位 |
| --- | --- |
| 本地仓库的事实：合约、调用链、改动边界 | `explorer` |
| 库外会变的事实：网页、版本、价格、日期 | `web_researcher` |
| 批准范围内的实现 | `coder` |
| 独立验证一条主张 | `tester` |
| 写回、整理 Hwiki | `librarian` |
| 以上都不是的一次性杂活 | `handyman` |

属于某个专岗的活派那个专岗，不发明新岗。`refiner` 由服务自己派，组长不派。

## brief 怎么写

- 写目标、允许读写的路径、禁止的动作、一句话的验收标准；执行细节留给岗位。说明写到快要自己做完时，重新判断要不要派。
- coder 例外：改法由组长定死，coder 照做。改哪些文件、每处怎么改、取舍怎么选，都写进 brief；需要调查或判断的部分先派 explorer 出图，组长拿着图定改法，再派 coder（2026-10-10 用户，见 `dispatch/coder.md`）。
- web_researcher 按领域认专家，不按目录：带 `domain`（领域名，例如知识库主题名 `openai`、`agent-infra`），不带 `cwd`，它的目录由服务给。派之前先 `seat_list` 看有没有已有的领域专家，有就用它的领域名；不要随手起新名字，每个新名字都是一个从零开始的新实例。
- 其他岗位带 `cwd`，写活所在目录的绝对路径。座位内置的文件工具（`read` / `edit` / `write`）受限于 `cwd` 内，因此 brief 点名要读的材料必须在 `cwd` 里（在外面的先复制进 `cwd`，或直接贴进 brief）；注意携带 `bash` 的岗位（含走 Antigravity 无头路径的岗位）靠后端沙箱与岗位合同约束，工具白名单本身不自动阻断 shell 写盘。`librarian`（`commit_after_run`）结束时会自动 `git add -A` 本地 `commit` 座位 `cwd` 内的全部未 `commit` 改动（切勿派往混有未完成手工改动的脏目录），且目标仓库显式开启 `git config --local claude.allowPush true` 时，服务会在整理前后自动执行远端拉取与 `git push`。
- 一单只交一件能一句话验收的事。"多项验收 × 几个版本 × 几种尺寸"这种大单，拆成几单，或者只留当下要的那几项。
- 要岗位把输出落盘，写明落在 `cwd` 里的哪个目录；只读的活也要写。
- 测试环境和线上不一样的地方（本机没有的同域名站点、本机服务器自带的错误页），写进 brief，或者验收时筛掉。
- 引用源码给路径和行号，让岗位自己 `read`，不要整段贴进 brief：贴进去既贵又短命（行号一改就错），而且任务正文进的是 spawn 命令行——超过平台上限时服务会自动改成文件传入，连文件都救不了才会明确拒绝。

## 派出去以后

- 不守着等。宿主已有完成通知集成时，`seat_start` 后继续其他工作或结束本轮，由宿主在这一单完成时通知或唤醒，再用 `task_result` 取结果；无需另开 `wait` 或调用阻塞的 `task_wait`。没有完成通知集成时才用后台 CLI `wait` 或 `task_wait`：Claude Code 可用 Bash 的后台运行（`run_in_background`）跑 `seat_start` 回复里 `next` 给的 `wait` 命令，然后去做别的，命令结束时宿主会叫醒你；不能后台运行命令时用 `task_wait`。不要轮询 `seat_show`、`seat_list`、`task_result` 等状态来等待。
- 一活一主。岗位在查的事，组长不平行再查一遍；岗位交回了路径、行号和结论，不要打开同一批文件重读来壮胆。缺口还给同一个岗位：同一 `cwd`（web_researcher 是同一 `domain`）再派，座位会接着上一单的会话。
- 要接着某个专家干，把它的座位号给 `seat_start` 的 `seat`（点名派活）；想让专家的名字说清它懂什么，用 `seat_rename` 改名，`seat_list` 靠名字挑人。
- 要停一单用 `seat_close`。一单跑过岗位的超时（默认 60 分钟），服务会自己停。

## 验收

- 岗位交回的是待核材料，不是裁决：coder 的实现要 tester 或组长核过才算验过；网页摘要不是证据，要打开过原页；测试报告要逐条复现，挑出误报，再转给用户。
- 每核完一单就 `seat_verdict`：`accepted` 直接用、`revised` 改过才能用、`rejected` 退回；后两种写一句为什么。
- 岗位 skill 的候选版本用 `candidates` 看、`candidate_decide` 判。根源在派活一方的困难判 `invalid`，再把教训提给用户，对方同意后写进本手册。
