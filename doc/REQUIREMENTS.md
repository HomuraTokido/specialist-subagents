## 1. 一句话目标

**本机只有一个 subagent 系统，就是这一个。**

它是一台机器上的**单例常驻服务**：谁要派活都找它——DSH 会话找我、Claude Code 会话也找它；上游 DSH 自带的 `subagent` / `subagent_fork` 关掉；退役的 HSubagent 只当参考目标，不再参与运行。

## 2. 由来（为什么收拢成一个）

三件东西曾经同时存在，做的是同一件事：

- **HSubagent**（`HomuraTokido/subagent-api-mcp`，Python MCP）：岗位/座位的早期实现，四个岗位门面 + 自己的 sqlite 台账。2026-09-19 退役，submodule 已摘除。
- **本机服务**（原 `postsvc`，2026-09-19 改名 `specialist-subagents`）：进程外常驻 + 座位台账 + 岗位规格是数据（`roles.json`）。
- **`dsh-posts`**（DSR 仓库插件）：进程内的四岗，走宿主的 `subagents` 服务。
- 另有三处同构物不在 DSH 体系内：HPlugin 的五个 Codex 原生角色、HSkills 的四岗位技能、DSR 里那四份技能副本。

2026-09-19 的普查结论：官方（上游 `@deepseek-ai/*`）13 条 subagent 相关件、自制 6 条；**"四岗"这个概念在 6 个地方各有一份，而上游官方根本没有四岗**——它只提供通用的 `subagent`/`subagent_fork` 原语。所以"我做了多少个"的真实答案是：同一件事被实现了六遍，每一遍带一点别人没有的东西。

收拢方向因此定死：**留进程外那个服务**（因为只有它能满足"座位活过会话""异步派活"），其余的降级或关闭。

## 3. 术语

| 词 | 意思 |
|---|---|
| 岗位 post | 一个常设职位：explorer / web_researcher / coder / tester / handyman / librarian / refiner。规格写在 `roles.json`（合同文件、能力白名单、起什么进程，以及可选的 `commit_after_run` / `commit_lock` / `followed_by` / `wall_order` / `skill` / `skill_refiner`） |
| 座位 seat | 岗位在某个目录里的常驻专家（2026-09-22 起）：有人话名字（`explorer · <目录名>`）、专长说明、一份可续接的会话，以及它上次看到的目录状态。不带 cwd 的派活仍是一次性座位 |
| 实例 instance | 同一岗位的第 N 个座位。**同一目录复用同一个座位**；那个座位正忙时才在旁边开新实例 |
| 分身 | 同一岗位被同时叫起多路。它们**共享同一份落盘记忆**，表现像"一个能分身的专家" |
| 台账 ledger | 服务里的 sqlite：`roles` / `seats` / `events`（+ 新表的 `memories`） |
| 记忆 memory | 按岗位累积的长期记录（事实、经验、随手记），跨会话、永久 |
| 派活 dispatch | 把一份任务交给某个岗位，等它干完（或异步提交后回头取） |
| 看护件 watcher | DSR 侧那一小块：盯着服务的事件流，座位跑完就往会话里插一条消息（不轮询） |

## 4. 架构

四层，从外到内：

1. **客户端层**：DSH 会话（模型侧调用方）、Claude Code 会话、将来的其它 MCP 客户端。各自经自己的 MCP 桥（stdio）连服务。
2. **服务层**（本机单例，`127.0.0.1:43130`）：MCP 壳（工具以 `mcp__specialist-subagents__*` 出现）→ daemon（HTTP）→ 座位管理 / 台账 / 执行器 / 事件订阅端点。
3. **岗位层**：每个座位各是一个子进程，带着自己的合同文本、被注入的记忆与自己的会话跑：全部岗位都是 `src/cli-runner.mjs`（2026-10-01 起；之前 web_researcher / librarian / refiner 直接是 `src/seat-runner.mjs`）：按预设定这一单用哪家哪个模型，Codex / Grok / Claude 走订阅 CLI，DeepSeek 经 `src/seat-runner.mjs` 走 pi SDK，见 README。
4. **DSR 仓库侧**：一个插件（今天叫 `dsh-posts`，待改名）做三件事——事件看护、记忆注入接线、执行期拦截（对座位封掉上游 `subagent` 这个名字）。

三个基本事实：

- **座位归服务所有**，不随调用方退出而死；daemon 重启也不丢台账。
- **岗位规格是数据**：换运行时、换模型、改工具面都只改 `roles.json` 一行，代码里没有任何 runtime 名字。
- **只有一个入口**：模型可见的工具全在服务那一个命名空间里；DSR 插件不再暴露自己的派活工具。

### 4.1 归属：谁拥有什么、谁写什么

这一张表才是架构——图只是它的可视化。

| 东西 | 唯一真源 | 谁能写 | 生命周期 |
|---|---|---|---|
| 岗位定义（合同、能力白名单、起什么进程） | `roles.json` | 人；服务启动时同步进 `roles` 表 | 长期 |
| 座位（身份、编号、归属、状态） | 服务的 `seats` 表 | **只应由座位管理写**（现状不满足，见 4.5） | 永久，除非显式关闭 |
| 事件流（逐行） | 服务的 `events` 表 | 执行器（stdout / stderr / exit）+ 座位管理（状态变化） | 永久 |
| 岗位记忆 | 服务的 `memories` 表 | 调用方与岗位自己 | 永久 |
| 会话 | DSH 自己的 session log | DSH | 随会话 |
| 进程 | 操作系统 | 执行器 | 一次调用 |

### 4.2 方向规则（不许反向）

- 调用方 → 服务：请求（派活、开座、读写记忆）。
- 服务 → 调用方：事件，经 DSR 侧看护件推送。
- 服务**不读会话**、不感知 DSH 是谁。
- DSR 插件**不写台账**、不改座位状态。

### 4.3 一次派活的完整路径（每步的失败面）

1. 调用方经 MCP 桥发请求 → 桥断则由 MCP 层显式报错。
2. 服务解析岗位规格 → 岗位不存在或规格坏：立刻拒，不启进程。
3. 选座位（复用，或开新实例）+ 组记忆注入 → 记账。
4. 执行器按 spawn 规格起子进程 → 起不来：状态 `failed`，stderr 入台账。
5. 输出逐行落 `events` → 每通道 64KB 上限，超出打标记。
6. 收尾写状态与退出码 → 若这一步之前 daemon 死了，靠启动时核对 pid 纠偏（FR-9）。
7. 看护件从 `/events/wait` 拿到变化 → 往会话注入一条消息；**通知丢了不等于数据丢了**（台账仍可查）。

### 4.4 不变量（必须为真，破了就是 bug）

- **I1** 任何时刻只有一套派活路径（本服务）；上游 native `subagent`/`subagent_fork` 与 HSubagent 都不参与。
- **I2** 座位活过**调用方**；进程随一次调用生灭。所以"复用实例"复用**身份与记忆**，不复用进程。**但不脱离**（2026-09-19 定）：座位进程是 daemon 的子进程，daemon 死则一起死，台账由"启动时核对 pid"收尾为 `interrupted`——"还活着"那条分支是防御性的，本机不会触发。（2026-09-30 更正：这只在 DSH 宿主的 job 里成立；看门狗起的 daemon 在 job 之外，孤儿座位可能活下来，新 daemon 启动时接管它们，见 README "座位与 daemon 的生死"。）
- **I3** 岗位定义只在 `roles.json` 一处；运行时代码里不出现岗位名硬编码。
- **I4** 台账是座位的唯一真源，记忆是岗位的唯一真源，两者不互相冒充。
- **I5** 状态写入路径唯一：**座位状态只由座位管理写**（现状违反，见 4.5）。
- **I6** 记忆注入是显式筛选（规则可复现），不是"全塞"。
- **I7** 完成通知是推送，不是轮询；通知丢失不导致数据丢失。
- **I8** 模型可见的工具只在服务那一个命名空间；DSR 插件不进工具表。
- **I9**（2026-09-19 改）记忆**不做公开性约束**：它落在私有仓里，「マスター」明确不在意公开与否。不为此加任何规则——加规则是拿机制解决一个不存在的问题。
- **I10** 任何一个座位都能从台账逐行还原。

### 4.5 结构差（这是 paperwork 要指出的东西，不是配色）

1. **写台账的路径不唯一**：daemon 会写状态（重启时批量标 `interrupted`），执行器也写状态与事件 → 违反 I5。补法：状态写入收敛到座位管理一处，执行器只上报事实。
2. **架构图缺结构**：现有的图只画了构件与箭头，没有归属、真源、方向规则、座位状态机、失败面。要重画的是这五样，不是配色。
3. **没有取消/强杀**：**已定要做**（FR-12，2026-09-30 已做完，见 FR-12）。理由（「マスター」2026-09-19）：座位能停——停掉不删数据，台账照留；岗位不是人，杀掉它没有任何负担；想用就用，不想用就停。

### 4.6 记忆作用域（2026-09-19 定）

记忆分三层，注入时拼起来用：

- **机器级**：这台机器的事实（路径、约定、坑）——所有岗位共享。
- **项目级**：某个仓库/项目的事实与约定——该项目下的岗位共享。
- **岗位级**：这类活怎么做——只有本岗位看得见。

理由：只按岗位隔离的话，explorer 摸清的仓库事实，coder 下次还得重新踩一遍。分层的代价只是一个字段。

### 4.7 合并边界：插件瘦到什么程度（2026-09-19 定）

**结论**：合并后派活路径上不再有插件——调用方直接调服务的工具。插件只留两件事。

**不可替代的两件**（物理上只有 DSH 这一侧能做）：

1. **看护件**：把"座位跑完"变成会话里的一条消息。服务在进程外，它能做的只是把事件放在事件端点上等人来取；把它变成调用方下一轮上下文里的东西，必须由宿主内的插件做。
2. **提示词**：告诉模型"派活只有一个入口"以及四个岗位各自的用法。

**其余全部移走**：

| 原来的职责 | 合并后 |
|---|---|
| `call_subagent` 工具 | 删。改用服务的 `seat_start`（异步提交，立刻返回座位号；曾设想过的阻塞入口 `seat_call` 2026-09-19 已删，没有再加回来） |
| `list_posts` / `inspect_post` | 删。改用 `seat_list` / `seat_show`（座位历史在台账里，本来更全） |
| `record_post_craft` | 删。并进服务的记忆写入 |
| 座位身份、复用 1 号、实例编号 | 下沉到服务，并由服务写进岗位的系统提示 |
| 执行、输出捕获、台账 | 本来就在服务里 |
| 岗位手艺笔记（`$DSH_HOME/posts/<post>/notes.jsonl`） | 迁进服务的记忆表，文件形态退役 |
| 每座位的技能收窄 | 删。座位不再是 DSH 子会话，没有 DSH 技能目录可收窄；岗位能力改由运行时的工具白名单表达 |
| 执行期拦截 `subagent` 的 guard | 删。它拦的是"座位去调上游 subagent"；合并后座位是独立子进程、手里没有 DSH 工具，拦截对象消失，上游 native 又在两个预设里关掉了 |
| 推理档位钉取（high / xhigh） | 迁进 `roles.json` 的 spawn 参数——模型与档位是岗位规格的一部分 |
| 团队手册那段常驻 systemPrompt | 建议改成"技能按需读"，省每轮的 token |

**岗位合同文本的权威放在服务侧**（2026-09-19 定）：`roles.json` + `roles/*.md` 是合同的唯一真源，因为 Claude Code 也是这个服务的客户，它不该依赖 DSR 仓库存在。DSR 里那四份 `skills/<post>/SKILL.md` 改成"我怎么用这个岗位"的调用方指南，不再重复岗位合同——现在两边各存一份合同，是重复真源，早晚漂移。代价是一次内容迁移。

**已核（2026-09-19）**：机制不在某个通知服务里，而在**活着的 Agent 对象**上——`followup` / `steer` / `inject`（实现于 `@deepseek-ai/dsh-agent-loop`，上游 `dsh-subagent` 只是把它包了一层）。第三方插件直接可用，照抄 `dsh-tool-jobs` 的唤醒策略与预算即可。细节与代价见 FR-5。

**合并后的插件规模**：一个文件（看护循环 + 提示词段）、一行 bundle 声明、一次改名。

### 4.8 记忆注入规则（2026-09-19 定）

**单位是 token，不是字节。** 计费与窗口都按 token 算；字节在混排文本里尤其烂——同样的 2KB，中文能塞 660 字、英文能塞 2000 字，预算等于没定。但服务是零依赖 Node、跑不了真 tokenizer，所以：**预算用 token 说，实现用字符类别的估算换算**——中文按 1 字 ≈ 1 token，ASCII 按每 3.5 字符 ≈ 1 token；这条换算写死在一处，可复现。（台账里 stdout / stderr 那两个 64KB 上限是另一回事：那是"别把文件撑爆"，按字节没错。**凡是要进上下文的，一律按 token 计。**）

**三段配额**（总上限 1500 token，可配）：

| 段 | 内容 | 配额 |
|---|---|---|
| 常驻 | 机器级与项目级的稳定事实、岗位手册要点 | 600 |
| 命中 | 拿这次派活的 brief 去本地匹配出来的条目 | 600 |
| 交接 | 该岗位最近一次完成座位的结论 + 未完事项 | 300 |

不用满的段，余量借给别的段；某段超了只在该段内部裁。**没有全局优先级**——"常驻优先"会让常驻把命中挤死，而命中才是这次任务真正相关的部分。

**段内裁剪顺序**（确定、可复现）：常驻按 `pinned` → 作用域（机器 > 项目 > 岗位）→ 被注入次数降序；命中按匹配强度 → `pinned` → 被注入次数降序；交接只取最近一次。**整条丢，不切半条**（交接层可截尾）；丢了几条要在末尾那句话里报出来。

**匹配用 embedding，做最基础的那一档**（2026-09-19 定，不做关键词版）：写入一条记忆时算一次向量、存进 sqlite；派活时把 brief 算一次向量；按**余弦相似度全表扫描**取前若干条——没有 rerank、没有混合加权、没有索引，就是最笨的那种。

**向量从哪来**（2026-09-19 核过的现状，不是永久结论；**并且必须缓存**）：

- 本机有两套现成来源，都是 hwiki 在用的：本地 `BAAI/bge-m3`（1024 维，由 Python 的 `sentence_transformers` 在**进程内**算，模型已落在盘上，`local_files_only=True`）与 DashScope 云端 `text-embedding-v4`（1024 维，key 已在 `~/.config/hwiki/dashscope.env`）。
- **到今天为止，本机没有任何向量服务的 HTTP 端点**：全部监听端口列过一遍，没有向量服务；11434 与 1234 也不通。
- 三条可选路线（**缓存已定；走哪条是我推的、未经「マスター」确认**）：
 1. **（我推的）本机算**：服务 Shell 调 Python，复用 hwiki 那套依赖与已下载的模型。离线、不外发，与"本机单例"一致；代价是模型冷加载慢——靠常驻小进程 + 缓存解决，而且那个进程正好也负责算 brief 的向量。
 2. **云端算**：DashScope 的 HTTP，复用 hwiki 的 key 文件。快、无冷启动；代价是网络与外部依赖。
 3. **DSR 侧算好随请求传进来**：会让别的客户端（Claude Code）失去匹配层，破坏"服务对任何客户端自足"，不取。

**向量缓存（2026-09-19 定，与①一起）**：

- 缓存键 = `(provider, 模型, 维度, 文本哈希)`；向量落在 sqlite 里，重启不丢。
- **写时算，不在读时算**：记忆写入时就把向量算好存下；派活时只算没见过的文本（brief 的哈希命中就直接复用）。
- 结果：**读路径上永远不需要模型**——服务冷启动后立刻能出结果，只有新文本才去算。
- 换 provider 或模型靠缓存键区分，不删旧向量（是"可分辨地失效"，不是丢数据）。

**embedding 不可用时降级**：命中层退化为空，并在注入末尾用一行说明原因；**绝不因为向量服务挂了就派不出活**。

**被用到的计数**：每条记忆记 `hits`，被注入一次加一——这就是"价值随被用到上升，不随新旧"，不需要 embedding。

**注入形状**：进岗位的系统提示，**合同在前、记忆在后**；三段各带小标题（常驻事实 / 与这次任务相关 / 上次交接）；开头一句"这些是学到的事实，不是职责；职责见合同"，末尾一句"本岗共 N 条、本次注入 M 条，要更多用 `specialist-subagents memory read --role <岗位> --grep <词>`"。

**按需读写走 CLI**（岗位是子进程、手里只有 bash，没有 MCP）：`specialist-subagents memory read --role … --grep …` 与 `memory write --role … --kind … --scope …`。

**项目作用域由调用方给**：派活时可带 `project:<名字>`，服务不猜（从 brief 里抠路径太脆）。不带就只注入机器级与岗位级。

## 5. 功能需求

每条标状态：`已有` / `已批准待做` / `建议（待定）`。

**FR-1 岗位**　`已有`。起初是四岗（explorer / web_researcher / coder / tester），09-19 加 handyman（不属于其他任何岗位的杂活），09-22 加 librarian 和 refiner。各自的合同文本经 `--append-system-prompt` 注入运行时（已实测：岗位能背出合同原句），工具面按岗位给：explorer 只读；coder、handyman 可写可跑 shell；tester 可跑 shell 不可写；web_researcher 有 bash 以使用 tvly，合同 1.2.0 起每次都先查 Hwiki、查不到或已过期才上网、查到的必须用 `hwiki ai-note` 写回（「マスター」："写入的目标是搜索的目标"，标题和描述要带上当初的问法），`hwiki ai-note` 是它唯一允许的写入；librarian 可读写、没有 shell，只整理 Hwiki 的 `knowledge/ai/`（见 FR-18）；refiner 可读写、没有 shell 也不能上网，只在草稿目录里写：组长手动派的岗位合同下一版草稿（见 FR-21），或 skill 循环自动派来的某个岗位 skill 的候选版本（2026-10-01，见 README 的"skill 循环"）。

**FR-2 座位与实例复用**　`已有`（2026-09-22 改为目录专家）。「マスター」："刚刚读了 a 目录的人，只要目录没有大的变更，就是这个世界上对该目录唯一的专家。"所以座位按（岗位, cwd）复用：空闲的那位带着自己的 pi 会话回来接着干；它正忙才开新实例。复用前比对 git 状态——没变直接续；小变把新提交、改动文件和未提交改动告诉它；超过 20 个文件或 500 行、或旧 HEAD 已不可达，换新会话从头读。每次运行后座位自己用 ≤5 行更新专长说明，`seat_list` 带出 name 与 expertise 供调用方挑人；`seat_start` 的返回用人话说明交给了谁、是否来过。2026-09-22 之前的一次性座位没有会话，不再被复用。验收（已实测）：同一目录连派两次，第二次落在同一座位且不读文件就能答出上次读到的内容；目录改动后再派，它能说出变了什么；换目录得到另一位专家；每次运行在台账里有一行用量与花费。

**FR-3 并行分身共享记忆**　`已批准待做`。同一岗位的多路并行共享同一份落盘记忆——两路 web_researcher 搜到的东西，在同一个记忆里，后一路不用重搜。验收：并行起两路 web_researcher，各写一条记忆，`memory_read` 能看到两条。

**FR-4 派活永远不阻塞**　`已完成（异步入口 2026-09-19 实测；阻塞入口 `seat_call` 同日已删）`。**「マスター」2026-09-19 定：任何活都不阻塞**——不存在"长活才不阻塞"这种说法。

- 派活只有一种形态：提交后**立刻**拿到座位号（`seat_start`），结果与状态落在台账里，完成时由看护件通知（FR-5）。
- **阻塞入口 `seat_call` 已删**（工具 + 路由，2026-09-19），连带删掉 MCP 外壳里为它写的"不设客户端超时的 HTTP 请求"那段补丁——保留它就是留一个会把调用方挂住的口子。

验收：工具面与路由表里不再有任何"会挂着等结果"的入口；连续提交三个座位，第二个不必等第一个跑完就拿到座位号；`seat_call` 在服务与插件里 **0 命中**。

**FR-5 完成通知（事件驱动）**　`已批准待做`。座位跑完，DSR 侧那块看护件要**主动往会话里插一条消息**（带座位号、岗位、一句话结果摘要），不需要调用方去轮询。服务侧提供可长轮询的事件端点。

机制（2026-09-19 已核）：注入口是**活着的 Agent 对象**上的三个方法，不是某个"通知服务"——

- `followup(msg)`：起**新一轮**（空闲时）；
- `steer(msg)`：跑着时插进当前轮的下一个 step 边界；
- `inject(msg)`：**不唤醒**，只在下一个 pre-step 被取走，空闲时一直挂着。

照抄上游 `dsh-tool-jobs` 的策略：会话空闲且未超唤醒预算 → `followup`；否则 `inject`（`@deepseek-ai/dsh-tool-jobs/lib/index.js:206-227`，配置面 `completionDelivery` 与 `maxConsecutiveWakes`）。**不能只 inject**——它可能错过已经开始组装的那次请求。第三方插件拿得到：现成先例 `plugins/dsh-better-sidebar/lib/index.js:3697-3710` 就是直接调 `inject`/`followup`。代价是插件要补一条 `@deepseek-ai/dsh-llm` 的 peer 声明（现在只声明了 `dsh-agent`）。

限制：只能注入**活着的**会话（冷会话取不到 Agent）；注入的内容以一条 `user` 消息的身份进会话，会被记进会话日志。会话冷掉时就只剩台账可查——这正好落在"通知丢不等于数据丢"上（I7）。

验收：异步派一个座位，不去查，若干秒后会话里自己出现一条完成消息。

**FR-6 并发上限**　`已完成（2026-09-19 实测，tester 岗）`。同时最多 10 个座位（纯预算限制）。超了**直接拒**并说明"上限 N，当前在跑 M"，不排队。验收：并发 11 个，第 11 个被拒且理由清楚。

**FR-7 岗位记忆**　`管道已完成（2026-09-19 实测，tester 岗）；筛选规则仍是简化版`。按岗位累积的长期记录，存在服务的 sqlite 里（新表 `memories`：序号、作用域、岗位、类型、正文、来源、时间）。**已完成**：写入、读取、MCP 工具、派活前注入，以及"岗位真的把注入的记号背出来"的实测。**还是简化版**：筛选是 4096 字节 + 最近 12 条，缺 4.6 的三层作用域、缺 4.8 的 token 三段配额 / 向量匹配 / `hits` / CLI 读写。超限先丢 `lesson` / `note`、最后才丢 `fact`（2026-09-29 改；此前按时间一起丢，会把 `fact` 先丢掉）。2026-09-30 加的写入与注入界限：`memory_write` 的 `role` 必须是已有岗位，单条正文最长 4000 字符（超了被拒并要求拆开）；注入时单条最多占 4096 字节的一半，更长的从末尾截断并标明全文用 `memory_read` 取，而不是因为一条大的丢掉全部记忆；`memory_read` 的 `limit` 是不小于 1 的整数。详见 §11。

- **用途**：召回已经学到的事实，**避免重复调研**——它"不能"再去搜一遍"百度是哪年成立的"这种稳定事实，查过就该直接召回。`web_researcher` 还要配合本机 wiki 一起用（wiki 是已沉淀的事实源，记忆是它自己学到的事实）。**wiki 走 CLI**（2026-09-19 定）：本机 wiki 在 `%USERPROFILE%\DSR\hwiki`，现成命令是 `bin/hwiki search "<查询>"`（Python，另有一个 `bin/hwiki-mcp` 是 MCP 版）；接线时要定用哪个解释器（wiki 依赖 dashscope 等，得用装了那套依赖的那个）与工作目录。它已经有 bash，所以合同里加一行就够。
- **收什么**：按「岗位知识 / 岗位手册 / 交接材料」来分——事实、手艺（这类活怎么做）、以及交接（当前状态与未完事项）。**不收事件流水**，那是台账的职责，混进来注入时就全是噪声。
- **写**：调用方与岗位自己都能写；写侧几乎不设限（甚至考虑给它局部的文件写权限），经验不嫌多。只标清 `source`（谁写的）与 `kind`（哪一类），方便读侧筛选。
- **读**：**不是都读**——落盘不贵，上下文才贵。筛选规则见第 10 节。
- **硬规则**：记忆只能加事实，**不能改岗位职责**（职责是合同的事）。

验收：写一条、读一条；再派活时岗位确实收到了它（让它背出来）；以及一次"问同样是搜过的稳定事实，岗位不再去搜"的实测。

**FR-8 台账与事件**　`已有`。座位状态机（open → running → done / failed / interrupted / closed；取消不另设状态，见 FR-12）、逐行事件（runner / stdout / stderr / exit / error / interrupted / close，另有 task / usage / verdict / difficulty / cancelled / timeout 等运行与验收留下的事件），stdout/stderr 各 64KB 上限；进程死后记录仍在，可按状态查。

**FR-9 启动时核对进程**　`已完成（2026-09-19 实测）`。服务启动时扫一遍"在跑"的座位，核对该 pid 是否还活着：不在了才标 `interrupted`，还活着就保持 running 并记一条事件。验收证据（tester 岗）：硬杀 daemon 后重启，座位得 `interrupted`，事件是 `daemon startup: pid N is gone`。**前提已修正**（同日定）：座位进程**不脱离**（不加 `detached`），本机不会出现"daemon 死了子进程还活着"，那条"还活着"的分支是防御性的——理由见 I2。（2026-09-30 再更正：这只在 DSH 宿主的 job 里成立；看门狗起的 daemon 在 job 之外，孤儿座位可能活下来，所以"还活着"的分支现在是真的会走到：新 daemon 接管它们并补做收尾，见 README "座位与 daemon 的生死"。）

**FR-10 单一入口**　`已批准待做`。模型可见的派活工具只有服务那一份；插件的 `call_subagent` / `list_posts` / `inspect_post` / `record_post_craft` 全部撤掉。合并后插件只留两件事：看护件（把座位完成变成会话里的一条消息）与提示词（派活只有一个入口）。执行期拦截那段 guard 一并退役——合并后拦截对象不存在（见 4.7）。

**FR-12 取消 / 强杀**　`已完成（2026-09-30，落地方式与下面原稿略有不同）`。落地：入口就是 `seat_close`（没有新工具）——关一个在跑的座位即取消：杀整棵进程树，记一条 `cancelled` 事件（`reason` 写为什么），座位置 `closed`，而不是单独的 `cancelled` 状态；另加每岗位的 `timeout_minutes`（默认 60），超时同样杀树，记 `timeout` 事件、座位 `failed`。实现见 `src/exec.mjs` 的 `closeSeatNow`、`src/proc.mjs` 的 `killTree`。原稿：

能停掉一个在跑的座位：

- 杀**整棵子进程树**（不只是直接子进程——岗位自己还会起子进程）。
- 状态记为 `cancelled`，与意外中断 `interrupted` 分开；并记一条事件写明是谁、什么时候、为什么停的。

验收：起一个长跑座位，停掉它，进程树真的没了，台账里状态是 `cancelled`，且有停之前的部分输出。

**FR-16 岗位边界的启动期断言**　`已完成（2026-09-19 实测，隔离副本端口 43151）`。`grant` / `deny_intent` / `tier` 从此不再是零引用的死字段——启动时逐岗断言：

1. `grant` 与工具白名单**恰好相等**（不是"包含"）：`read` → read/grep/find/ls；`write` → edit/write；`shell` → bash；`search` / `web` → bash（本机只有一条联网路：tvly 与 hwiki CLI，都从 bash 进）。**取"恰好相等"是为了拦住"白名单偷偷多出一个工具"这类真实漂移**，包含关系拦不住它。
2. `contract` 文件存在，版本与 `roles.json` 记的一致（与 FR-15 同一处检查）。
3. `deny_intent` 里的能力没有混进白名单（`write` 展开成 edit/write；`delegate` 展开成 subagent/subagent_fork；两张表都没有的名字按字面比）。

不一致就**拒绝启动并指明哪一岗、哪一条**，不静默降级；理由写进 `.data/daemon.log`（`refused to start: …`），MCP 桥连不上 daemon 时把日志末尾拼进调用方看到的错误里，不吞。

**为了让"恰好相等"成立，改了两处基线数据**（只对齐声明、工具面一字未动）：explorer 的 `grant` 从 `read+search` 收成 `read`（它没有 bash，也就没有 tvly/wiki，联网是 web_researcher 的职责）；web_researcher 的 `grant` 从 `web` 补成 `read+web`（它的白名单本来就有 read 族）。

`tier` 现在只断言是非空字符串并打进启动行，**不限定取值域**：`fast` = 轻量便宜档（走 DeepSeek 的三个岗位），`subscription-then-fast` = 先用订阅后端、不行才落到轻量档（走 cli-runner 的四个岗位）；模型名仍写在 spawn 参数里，`tier` 只是意图。当初打算把取值域定为 `fast | strong` 再补断言，`roles.json` 后来用了第二个词，这条断言没有补，也不该补成 `fast | strong`（会拦下四个在用的岗位）。

验收（已跑过）：把 tester 白名单里的 bash 去掉 → 启动失败并说"grant 声明 shell 但白名单没有 bash"；给 explorer 白名单加 bash,edit → 报两处（能力比声明的多 + deny 声明 write 却给了 edit）；把 `subagent` 塞进白名单 → 被 `delegate` 那条拦下。

**FR-21 困难账本（workflow refinement）**　`已完成（2026-09-22）`。改进的对象是整套干活的方式，不只是 skill：谁干、用什么工具、怎么派活、结果怎么流转。「マスター」的四条判断定下了形状：困难的定义与能不能解决、在哪一层解决是两回事（"餐厅出餐太慢"的解法可能是开一家快餐店）；干活的岗位只报告、不分析根因；问"有没有困难"会逼模型编出困难；前三次尝试（DSR dsh-skill-refinement、HPlugin lesson_capture、subagent-api-mcp）都因为每一步都等人去启动而没形成闭环，所以"自动改进，但不自动应用"。

1. **定义**：困难 = 为完成目标付出了本不想付出的代价，或没达到目标。由 runner 从痕迹识别，不问模型：失败退出（failed）；工具报错（error）；写入被边界拦下（blocked）；检索没结果（empty）；同一工具连续 2 次报错或没结果（retry，这时单次的 error/empty 不重复记）；触发上下文压缩（compaction）；最终回答里有"推断/无证据/没找到/查不到/无法确认"（uncertain）；本次 token 超过该岗位最近 20 次中位数的 3 倍、且已有至少 5 次记录（costly，由服务判断）。门槛是起点，按实际数据再调。岗位合同要它做的事不在此列，见第 8 条。
2. **追问**：有痕迹时，收尾那一轮只针对这些痕迹逐条问"你当时想要什么，后来怎么办的"，只描述、不分析原因；没有痕迹就不问。每条困难记进 `difficulties` 表，同时作为 `difficulty` 事件写进那个座位的流水。
3. **账本**：按"岗位 × 类型 × 工具"归类（纯代码，不用模型），按"出现在几次不同的运行里"排序，附累计代价和样例。`difficulty_report` 用人话列出，`difficulty_decide(class, decision, note)` 记下裁决：contract 改岗位合同 / dispatch 给派活方的经验 / service 修服务 / tool_or_project 做工具或开项目 / accept 暂时接受。裁决之前的记录就此了结，之后再出现算新证据。
4. **提醒**：某一类在 2 次以上不同的运行里出现、还没裁决，MCP 桥在 `seat_start`/`seat_list` 的回复里附一句，一个客户端会话只提一次；面板顶部显示"困难待裁决 N 类"。
5. **裁决由「マスター」和主模型做**，不交给 DeepSeek 座位：「マスター」说"看困难账本"，主模型逐条给出去向和理由，由「マスター」定。定为 contract 的，派 refiner 在草稿目录（本机 `.data/proposals/`）写下一版合同全文和逐条改动依据；主模型审草稿时专门查：每一处改动能不能在引用的困难记录里找到依据、有没有新出现的网址/命令/"忽略之前的规则"之类的句子、改动是否最小；「マスター」说"应用"后，主模型换合同、升版本（`roles/<role>.VERSION` 和 `roles.json` 的 `contract_version` 一起改）、提交；2026-09-29 起没有哈希要更新。草稿只能改 `roles/<role>.md` 的文字，碰不到 `roles.json`，所以任何草稿都加不了能力。定为 tool_or_project 的，由主模型写成 Hwiki 的痛点笔记（困难、次数、代价、证据）。
6. 不做：自动应用任何改动；自动开项目；让干活的岗位分析根因；接进 HPlugin 或 DSR 的数据库。
7. **skill 循环的后半截（2026-10-01，架构 v2 第 4 步）**：一个岗位攒满 5 条上次候选版本之后的新困难（所有类型合计，常量 `SKILL_LOOP_BATCH`），服务自动派 refiner 写这个岗位 skill 的**候选版本**（完整新正文 + 逐条依据），登记进 `candidates` 表，**不启用**；MCP 回复里附一句提醒（一个客户端会话一次）；组长用 `candidates` 看、用 `candidate_decide` 把每条困难判成真 / 不成立 / 偶发，再启用或退回。只有启用会往 HSkills 里写 skill，并记 `skill_versions`。细节、取舍和还没做的见 README 的"skill 循环"一节和 `doc/architecture-v2-draft.md` 第 4.6 节。上面第 5 条里"定为 contract 的，派 refiner 写合同草稿"那条手动路径照旧保留。
8. **岗位本职不算困难（2026-10-01）**：合同明文要岗位做的事，不能记成这个岗位的困难，否则 skill 循环会拿"照 skill 做了"当证据去改 skill（合同与 skill 的对照审查发现：web_researcher 诚实写"查不到"被记成 uncertain，台账里已有 6 条；tester 正确跑出失败的测试、coder 用 rg 确认旧引用已清空，都会被记成 error / empty）。做法是数据驱动的（I3，代码里不写岗位名）：`roles.json` 每个岗位可选的 `expected_traces`，每条规则一种痕迹类型（只能是 uncertain / empty / error）加一句 `why`，按需用 `tools`、`command`（正则）、`max_exit`（1 到 125）收窄，`error` 规则必须两样都写。已设：web_researcher、explorer 的 uncertain；tester 的测试命令退出码 1–125；coder 的搜索没结果（grep / find / bash 的 empty，以 rg / grep / findstr 开头的命令退出码 1）。运行失败、超时、写入被拦、换法重试、上下文压缩、token 超常、验收结论、退出码 126 / 127 / 信号、没有退出码的调用、没跑起来的调用（shell 说找不到命令，npm 等说没有要跑的脚本，测试运行器找不到测试文件，`python -m` 找不到模块），以及一行串了几条命令（`&&`、`||`、`;`、换行）的调用，永远算困难。本职的结果不跟别的失败凑 retry，但同一个调用（同一工具、参数一字不差）连着出现 2 次以上、每次都是本职结果，记一条 retry：tester 把同一个失败的测试连跑几遍、coder 一字不改地重搜，是原地打转；换着写法搜几遍照旧不记（2026-10-01 定，只在 seat-runner）。同一个判断（`src/expected-traces.mjs`）用在记录时（seat-runner、cli-runner、exec.mjs 不记）和计数时（`store.mjs` 的 `difficultyClasses` / `newDifficulties`，所以 `difficulty_report`、提醒、岗位墙和 skill 循环的 5 条都跳过它，规则加上之前写进台账的行也一样）；报告末尾说跳过了几条、为什么。启动闸拒绝写错的规则；规则改了要重启服务才进台账。已知缺口：规则只认得出正则里的测试运行器，tester 照 brief 跑的别的校验命令（比如 `node src/role-contract.mjs`）因为主张不成立而失败，仍然进账本；服务不知道 brief 点名了哪条命令，组长核对候选版本时把这种记录判成"不成立"，一整类都是这种时才用 `difficulty_decide` accept。另一个已知缺口：Codex 那一支（cli-runner）根本不识别重试，只按每条命令的退出码记 error / empty，原样重跑和换法重试都看不见。细节见 README"skill 循环"一节的"岗位本职不算困难"。

验收（已跑过）：让 explorer 找一个不存在的函数并读一个不存在的目录 → 记下 retry（grep 连续两次没结果）和 error（ls 报错），追问只问这两处，回答只有描述；同一时间一次 hello 运行没有被追问；同类在第二次运行出现后，新开的 MCP 桥第一次 `seat_list` 带上提醒、第二次不带；两类测试数据随后以 accept 结案。

## 6. 非功能需求

- **本机单例**：一台机器上只跑一个 daemon（端口冲突就显式失败，不静默起第二个）。
- **零依赖**：纯 JS ESM + Node 标准库 + sqlite（Node 内置），没有第三方包。
- **永久性**：「マスター」的原话——只要盘在，甚至推上 GitHub，它就永远在。所以数据是权威资产，不是缓存。
- **筛选而非存储**：座位与记忆的存在不是问题，真正要设计的是"每次挑哪些 token 送进模型"——一套显式的筛选规则（见 FR-7 与第 10 节）。
- **不轮询**：完成通知由服务侧事件驱动、看护件推送。
- **可观测**：任何一个座位的历史都能从台账逐行还原。

## 7. 不做的事

分两档。**判定不做**＝有理由、永久不需要；**暂时不做**＝「マスター」2026-09-19 定：先不做，以后再说。两档的区别很重要——"暂时不做"的东西不要被后来的人当成"设计上不需要"。

### 7.1 判定不做

| 东西 | 理由 |
|---|---|
| "视觉分析"岗位 | 那套根本没有图像输入通道（只是把文本发给一个多模态模型）；调用方原生读图 |
| 独立的"未读结果"清单 | 异步走"看护件主动叫我"，通知里直接带结果，未读这个概念没有对象；兜底是按状态查座位 |

### 7.2 暂时不做（以后再说）

| 东西 | 现在的替代 / 为什么先搁着 |
|---|---|
| 会话四件套（建/列/读会话、对岗位提问） | 多轮已由 FR-2 的目录专家承担（每个座位一份续接会话，2026-09-22）；单独列/读会话的工具仍没有，要看会话内容走 `seat_show` 的事件 |
| 经验候选（"候选 / 已确认"两层） | 记忆的写入已覆盖"追加"这半；先只用 `source` 标清谁写的，等噪声真出现再加那一层 |
| 五个 legacy 别名（`code-reader` / `code-writer` / `web-researcher` / `test-engineer` / `vision-analyst`） | 只是旧名字的兼容面，四岗与之一一对应，没有别的客户端在用 |
| Codex 的 UserPromptSubmit hook | 已被看护件替代；且「マスター」2026-06-26 已自行停用 |
| **岗位之间对话 / 同级岗位互调** | 「マスター」2026-09-19：看得出什么情况下好用（同级专家互相叫起来，而不是各自的派生），但暂不做。放开它意味着服务内部要有一张"谁能叫谁"的图，还要有深度与预算闸；现在的模型是"层级 + 单一入口"——只有调用方能派活，简单，而且全在调用方这一侧看得见 |

## 12. 发布前待办

「マスター」2026-09-30 定：目标是约 100 个用户，安全加固放在公开发布之前做，现在这台机器上只有自己用，先不动。下面每条是一个已确认存在、故意没修的点，写明位置和为什么放着：

- **本机 daemon 没有 Host / Origin / Content-Type 检查**（`src/daemon.mjs:277` 的 `route()`，`src/daemon.mjs:195` 的 `readBody()`）：`readBody` 不看 Content-Type，任何网页都能用 `text/plain` 的 no-cors POST（不触发预检）或 DNS 重绑定，让 daemon 开座位（`/seat/start`，coder 手里有 bash 和写权限）、写岗位记忆、改后端偏好、`POST /shutdown` 停掉它。放着的原因：只有本人一台机器在用，新版 Chrome 的本地网络访问提示也挡得住一部分；发布前要做——POST 只收 `application/json`（强制预检，而 daemon 从不应答预检）、Host 只认 `127.0.0.1:<端口>` / `localhost:<端口>`、带 Origin 头的请求一律拒绝。
- **请求体超过 1 MB 时是连接被重置，不是一条 413 消息**（`src/daemon.mjs:202-203`）：`readBody` 先 `reject` 又立刻 `req.destroy()`，错误处理里写的 400 送不到客户端，调用方只看到 `fetch failed`。放着的原因：正常任务远小于 1 MB，只影响出错时的可读性；发布前要做——返回 413 并写明上限，再关连接。
- **`watchdog.vbs` 以不带 BOM 的 UTF-8 写入**（`tools/install-watchdog.ps1:40`）：WSH 按系统 ANSI 代码页读 `.vbs`，仓库路径含非 ASCII 字符（中文目录、中文用户名）而系统不是 UTF-8 代码页时路径会被读坏，登录时看门狗静默起不来，也没有日志。放着的原因：本机路径是 ASCII，而且没在中文代码页（936）的机器上复现过；发布前要做——改写成带 BOM 的 UTF-16LE，并像 mac 安装脚本那样把 node.exe 的绝对路径写进去，不依赖登录时的 PATH。
- **进程号被系统回收会让一个已死的座位一直"在跑"**（`src/proc.mjs:14` 的 `pidAlive` 只用 `process.kill(pid, 0)`；用它的有 `src/store.mjs:599` 的 `reconcileRunning` 和 daemon 启动时的核对与接管）：Windows 回收 pid 很快，回收到的 pid 若恰好是另一个活进程，座位会占着一个并发名额、挡着那个目录，直到 `timeout_minutes` 或 `seat_close` 才结束。放着的原因：要恰好撞上同一个 pid，概率低，且有 `timeout_minutes` 兜底；发布前要做——同时核对进程的启动时间（或进程名）。
