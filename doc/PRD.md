# PRD：specialist-subagents

2026-10-10 起草。起草人是 Claude Code 主会话（Opus 5.5），依据是当天和「マスター」的讨论。这份文件取代 `doc/REQUIREMENTS.md` 成为本服务唯一的权威需求：REQUIREMENTS 的 FR-1 到 FR-21 全部并进来，每条都标了原编号，一条没删；REQUIREMENTS 留作历史。

## 0. 这份文件怎么用

这几条是写给以后每一个读它、改它、照它写代码的模型的，不是建议。

1. **需求本身只有两种终态：已实现、未实现。** 状态只由 `node tools/prd-check.mjs` 给出（见 P-1），它把每条需求的验收跑一遍。对依赖宿主配置、真实台账或真模型凭据的 8 项本地检查，检查器会额外输出第三种状态「需要本机」；干净克隆上因此以退出码 1 结束，见 `README.md`。这表示证据依赖本机，不新增需求终态。文件里不写"已完成"，任何人、任何模型说"做完了"都不算数，检查命令说已实现才算。
2. **实现的人无权删除、暂停、推迟、缩小任何一条需求。** 前提没立住，就先把前提做出来；依赖关系写进第 6 节的实施顺序，不写成"先不做""暂时停掉""这次不碰"。为什么：本项目已经重做过好几轮，每一轮的想法都对，代码却一轮轮把它写丢了，丢法就是这样一刀一刀切掉的（2026-10-10，主会话当场演示了两次：想把四名词重构划成"不做"，想停掉 skill 循环）。
3. **只有仓库拥有者（上游仓库中称「マスター」；在外部 fork 或独立部署中指该副本的维护者本人）能改范围。** 改了就在这份文件里改那一条，写日期和ta的原话。没有"暂时不做"这个类别：要么是需求，要么是ta判定不做（第 5 节）。
4. **先改 PRD，再改代码。** 代码和 PRD 冲突时，以 PRD 为准，把代码改回来；PRD 本身错了，先回去问ta。
5. **每条需求的格式**：编号、要什么、为什么、验收（必须能执行：一个测试，或者一条对台账的查询）、依赖。写不出可执行验收的需求，说明它还没想清楚，回第 7 节讨论，不进需求表。
6. **"做完"以端到端为准。** 验收分两层：上层是第 4.0 节的端到端场景，走完整的真实链路；下层是每条需求自己的测试，只用来定位场景坏在哪一步。一条需求只有在它自己的测试通过、并且覆盖它的每个端到端场景都通过时，才算已实现。最终的端到端是真实使用：场景全过而 C-6 的真实数字不达标，说明还有场景没想到，要补场景。为什么：本项目过去每个零件单独看都"做完了"、测试是绿的，可组长派活到专家接上理解这一整条路，续接率只有 20%（2026-10-10「マスター」："总之需要端到端"）。文档和图都是中间产物，不能替代整条链路真跑一遍。

## 1. 目的

让干过活的 AI 不随会话消失：它懂的东西有地方落、有名字能找到，下次接着用，而不是"反复解决同一个问题，但是重来很多遍"（「マスター」，2026-09-22）。

这是一个**仿生的 AI 组织**：精确地拿人类组织架构来映射 AI（2026-10-10「マスター」："这是仿生学"）。人类组织靠稳定的岗位让专家成长，任务来来去去，岗位一直在；本服务要给每个角色一批持久、可点名、会积累的专家。组长（主模型）遇到问题去问懂那一块的专家，即使自己查得到也不自己查——专家的上下文里已经装着原文，它多想一步，组长要从头再付一遍（2026-10-10「マスター」："术业有专攻""直接去问专家"）。

它跨宿主：任何能接 MCP 的 agent 宿主都经同一个 MCP 接入同一批专家。宿主名单不写死：「マスター」在用的有 Claude Code、Codex、DSR、Grok、opencode、openclaw 等，以后还会变；需求里出现具体宿主名的地方只是例子。起草时曾定位为个人内部工具（2026-10-10 初稿注记；2026-11 已正式以 MIT 许可证作为通用开源编排服务发布，代码注释与 PRD 中保留的「マスター」指代原作者 / 仓库维护者）；岗位墙上有脸、有战绩的角色本身就是产出之一。

背景材料：`doc/lineage.md`（谱系；作者本地历史笔记，未随仓收录）、「マスター」的文章 Why Self-Evolution Belongs to Subagents（https://homura-tokido.com/subagent-evolution.html ，2026-05-07）、`doc/review-2026-10-01-intent-and-direction.md`（10-01 评审与台账数据；作者本地历史笔记，未随仓收录）。

## 2. 术语

术语会反过来约束代码结构（roomAImate："如果叫 budget_guard，它容易被写成限流器"）。对外的 API、文档、岗位墙一律用下面的词。

| 词 | 是什么 | 不是什么 |
|---|---|---|
| **角色**（岗位） | 一种手艺的规格：合同、工具白名单、后端顺序、skill。岗位墙上的一张脸。数据在 `roles.json` | 不是一个进程，也不是一个人 |
| **对象** | 专家懂的那一块：一个目录，或一个领域（例如 Hwiki 的主题名 `openai`、`agent-infra`） | |
| **专家** | 某个角色在某个对象上的持久身份：一个有语义的名字，加上它积累下来的全部**记录**。可点名 | 不是会话，不是工位，不是空白实例 |
| **记录** | 专家名下所有原始材料：每一单的会话日志、报告、交接文档。原文一律留在磁盘上 | 不是摘要 |
| **一单** | 组长派给一个专家的一次活，到终态不再变 | |
| **分身** | 专家正忙时，带着它的记录并行接活的另一个实例，记录归回同一个专家 | 不是空白新实例 |
| **交接** | 专家把自己懂的、没做完的、踩过的坑写给接手者的文档；会话续不上或合并时用 | 不是一两句专长说明 |
| **名录** | 所有活着的专家：名字、角色、对象、专长，给组长挑人用 | |
| **组长** | 派活方（主模型）：定目标、路由、裁决、验收；坐在任意一个接了 MCP 的宿主里 | 不是又一个工人 |
| **宿主** | 组长所在的 agent 客户端（Claude Code、Codex、DSR、Grok、opencode、openclaw……），名单不写死 | 不是后端 |
| **后端** | 专家这一单由谁执行：预设里排好的 CLI 和模型，可增减 | 不是专家；换后端不等于换专家 |
| **临时工** | 没有任何记录就开工的一单。本服务把它当缺陷统计（见 C-6） | |

内部的表名和座位号（`seats`、`seat-coder-16`）保留作键，保证兼容；对外文字不再用"座位"。

2026-11 注：MCP 工具名（`seat_start`、`seat_list` 等）、CLI 子命令与座位号（`seat-coder-16`）作为稳定公开协议标识符保留「座位 / `seat`」命名。上句指概念模型与岗位墙将持久身份定义为「专家」而非空白工位；`README.md` 与 `doc/connect.md` 介绍接口参数时据此称「座位（持久专家槽位）」。

## 3. 设计原则

- **问专家。** 关于某一块的问题送到懂那一块的专家那里问，用它的回答；组长不凭摘要自己下判断，也不为核对再外包一层。
- **仿生，偏离要有理由。** 每个机制先问"在人类组织里这是什么、怎么做"，照着映射；只在 AI 真的不同的地方有意偏离，并写明理由。已知的偏离：AI 能分身（所以专家忙时开分身，不排队）；AI 读得极快（所以可以现场读原文）；AI 没有私心、不累（所以不需要激励和防扯皮的机制）。
- **先持久，再专精，后进化——这是实施顺序，不是取舍。** 不持久，自我迭代就没有主体；分布不窄，经验不收敛（「マスター」的文章）。三者都要实现。
- **记录是文字，会话是记录的一种。** 对模型来说，"续接会话"就是把那份日志重新灌进上下文，和灌一份文档是同一件事。所以会话"断了"永远不等于记忆丢了，只是这一单换一种装载方式。
- **压缩要晚、要少，原文不扔。** 摘要只记得出了什么结论，不记看过什么；"这条是不是新的"只有原文能回答（2026-10-10「マスター」）。专家的价值是它那份没怎么压缩的上下文。
- **粒度要细。** 一个专家只管一小块，原文才装得下、压缩来得晚、经验才收敛（2026-10-10「マスター」："细的才不会那么容易爆上下文"）。
- **名字是写给模型读的。** 组长靠名字挑专家，名字要说清它懂什么（2026-10-10「マスター」："不是给人看的，是给你看的"）。

## 4. 需求

### 4.0 端到端场景

每个场景走完整的真实链路：组长经 MCP 派活 → 服务挑专家、装载记录 → 后端执行 → 结果落进台账，组长取回结果。每个场景跑两种后端：假后端（每次 `prd-check` 都跑，快、免费）和一个便宜的真模型（每一期验收时至少跑一遍，结果存档）。场景用今天真实踩过的坑来写，断言看的是结果，不看内部走了哪个函数。

**T-1 同一个问题问两次。** 组长问某个领域专家一个事实问题；换一个 MCP 客户端会话后再问同一个问题。断言：第二次那一单不发起任何联网或 Hwiki 调用，回答注明出自上一单、带查证日期。覆盖：E-2、E-3、E-4、C-1、B-1、O-1、O-5。

**T-2 目录大改之后接着干。** coder 专家在某个仓库干一单；之后这个仓库改动 30 个文件、500 行以上；再派一单问它"上次你改了什么、现在变了什么"。断言：第二单续上原来的理解，答得出上一单的改动，也答得出这次的变化。覆盖：C-2、C-5、E-3。

**T-3 专家正忙时再来一单。** 专家在跑一单（假后端里设成慢），同时再派给它一单。断言：第二单立刻拿到返回、带着专家的记录开工、答得出专家此前读到的内容；两单跑完后都记在同一个专家名下，下一单能看到两单的记录。覆盖：C-3、O-1、O-3、C-5。

**T-4 合并。** 专家 A 在对象上干过一单，读到一个只有它知道的事实；把 A 合并进 B；再派给 B 一单问那个事实。断言：B 答得出来；A 已归档、不在名录里；再下一单 B 的任务前缀里不再附交接。覆盖：L-1、L-2、E-2、E-6。

**T-5 取消一单，专家还在。** 专家在跑一单时取消这一单；随后再派给同一个专家一单。用 `task_cancel` 取消。断言：被取消的那一单进程树没了、记 `cancelled`；专家仍在名录里，下一单接着它此前的理解。覆盖：L-5、L-2、E-6。

**T-6 换后端。** 同一个专家的第一单用后端甲跑，第二单强制用后端乙跑，问第一单里读到的内容。断言：第二单答得出来，任务前缀或上下文里有第一单的记录。覆盖：C-1、C-5。

**T-7 新开专家的名字和点名。** 派给一个从没碰过的对象，服务新开专家；组长给它改语义名，再按座位号点名派一单。断言：回复说清交给了谁、是新开的；名录里是新名字；点名那一单落在同一个专家上。覆盖：E-1、E-2、E-3、E-5、E-6。

**T-8 学习闭环。** 某个角色的专家在几单里累计 5 条困难；服务派 refiner 写候选；组长审核启用；该角色下一单开工。断言：下一单带的是新 skill（事件里记了版本）；handyman 累计 5 条困难时没有派 refiner。覆盖：S-1、S-2、S-3。

**T-9 收尾只保留真正未完成的工作。** 同一专家连续接单：完成 hello 和记忆暗号任务，不因未读记录路径、未执行岗位常规动作或明确禁止的动作产生新待办；任务有一个因缺输入未完成的明确要求时，清单保留它；下一单无关 hello 不清空这个真正的旧待办，也不自动执行它；补齐输入、完成该要求后清空。旧清单中有证据表明原任务未要求或禁止的事项应剔除，不能确认的真正历史工作不擅自删除。覆盖：O-5。2026-10-11「マスター」针对 hello 和暗号续接中的清单污染要求“修”。

**T-10 做到一半被拦截，换一个不带历史的新会话接着做完。** Claude 后端的专家在一个 git 仓库里干过一单，会话里有一个只有它知道的事实；第二单做到一半（写了一个停在函数中间的文件）被后端模型的安全过滤拦下。断言：这一单最终做完，结果是接手会话的结果，开头列出被拦时改动过的文件和增删行数；接手的会话做完了那个文件，答不出旧会话里的事实（不带历史）；事件里记了一次拦截和接手；专家下一单仍续它自己的会话，答得出那个事实，并被告知目录里变了什么；再派一单不带上下文的分身问那个事实，分身答不出，专家本人仍是原来那个。拦截那一腿用假 Claude（真模型不能按需触发拦截），接手那一腿在 `--real` 下是真模型。覆盖：O-6、C-7。2026-10-24，DSR 主会话三单 coder 一分钟内全被拦在半路，组长只好自己补完。

场景随真实使用补充：C-6 的真实数字不达标、或「マスター」遇到一种新的失败方式，就写一个复现它的场景加进来。

### 4.1 专家与寻址

**E-1 专家有语义名字。** 每个专家的名字说清它懂什么（例如"explorer · 座位与 skill 循环"），不是"岗位 · 目录名"的自动拼接。新专家开出来时由服务按对象起一个初始名，之后由组长在合并、拆分或过名录时改成语义名（E-5）。领域专家的对象名用 Hwiki 主题名（2026-10-11 主会话定，依据 `doc/goal.md`）。为什么：组长靠名字挑人。验收：`seat_list` 默认视图里没有两个活着的专家同名；新开的专家名字里不含座位号。依赖：E-5。

**E-2 点名派活。** `seat_start` 收专家的座位号，就交给这个专家：续上它的会话，或按 C-1 装载它的记录。角色对不上、专家已归档时拒绝，消息写清原因和下一步。专家正忙时按 C-3 开分身。为什么："问专家"的前提是能叫出名字；HSubagent（2026-09-10）就有 `ask_session` 点名，后来丢了。验收：新写测试——点名派两单，第二单接着第一单的会话；点名一个已归档的专家被拒。

**E-3 自动挑专家并说清挑了谁。** 不点名时，按对象自动挑：目录角色按真实路径，领域角色按领域名（原 FR-2，2026-10-10 加领域）。对象允许写成"目录 + 主题"，主题可以不填；目录拆分后匹配不上唯一的专家时，列候选让组长点名（2026-10-11 主会话定，依据 `doc/goal.md`）。没有合适的专家就新开一个，并在回复里说清"交给了谁、它来过几次、为什么是它"。主题是对象的一部分，带了就严格匹配（2026-10-24，修 todo.md 的 bug：DSR 下 tester 只有一位没主题的专家，带新 topic 派单仍落在它身上，没有开出新专家）：带 topic 时交给同主题的专家，这个目录还没有这个主题的专家就新开一位，回复里列出同目录的其他专家（topic 写错时一眼看得出）；不带 topic 时，目录里只有一位专家就交给它，有几位就交给没有主题的那位，没有或不止一位没主题的就拒绝并列候选。为什么：随手派活要便宜，挑人要透明。验收：`tests/directory.test.mjs` 的目录专家与领域专家用例和主题用例（单一无主题专家 + 新 topic → 新专家；不带 topic 仍回无主题的那位）；回复的 `note` 写明专家名和是否来过。

**E-4 按领域认专家。** `roles.json` 里 `expert_by: "domain"` 的角色（现在是 web_researcher）按领域认专家，不按目录；传了 `cwd` 或没传 `domain` 就拒绝，并列出已有领域。验收：`tests/directory.test.mjs` 的"a domain expert"、`tests/entry.test.mjs` 的拒绝用例。

**E-5 改名。** 组长能给任何专家改名。验收：新写测试——改名后 `seat_list` 显示新名字，座位号不变。

**E-6 名录。** `seat_list` 默认只列活着的专家，每人一行：名字、角色、对象、状态、来过几次、专长；能按角色、目录、领域过滤。为什么：名录就是"谁懂什么"的地图，组长靠它路由，不另设路由座位。验收：`tests/entry.test.mjs` 的视图形状用例，加上按领域过滤的用例。

**E-7 名录里没有重复专家。** 同一个对象从不同路径进来（junction、符号链接、大小写不同）认作同一个专家。大小写只在不区分大小写的文件系统上合并：Linux 上 `/a/Foo` 和 `/a/foo` 可能真是两个目录（2026-10-11 主会话定，依据 `doc/goal.md`）。验收：新写测试——经 junction 和真实路径各派一单，落到同一个专家。

### 4.2 记录与连续性

**C-1 不从零开始。** 派给已有专家的一单，必须带着它的记录开工：能续上会话就续；续不上（换后端、会话文件被别的后端占着）就把它最近的会话日志当文字装进去，装不下就装交接文档加原文路径。交接只在会出事的节点写，不定期刷新：会话快超过该后端上下文的一半时（L-4 的阈值）、换后端之前、合并或拆分时；节点之后又干的几单不在交接里，靠交接里的原始记录路径补（2026-10-11 主会话定，依据 `doc/goal.md`）。为什么：会话文件一直在磁盘上，"续不上"只是装载方式的问题。验收：新写测试——同一个专家换后端派第二单，它能答出第一单里读到的内容。

**C-2 目录变了不丢会话。** 目录改动多少都续上原会话，附一份变化说明；原 FR-2 里"超过 20 个文件或 500 行换新会话"的规则取消。为什么：项目越活跃越需要连续性；10-01 评审的台账里 20 单因为这条被强制换新。验收：新写测试——改 30 个文件后派单，专家接着原会话，任务前面附了变化说明。

**C-3 专家正忙时开分身，不开空白实例。** 分身带着专家的记录开工（pi 复制会话文件，其他后端按 C-1 装载），跑完后它的会话日志和报告归入同一个专家的记录。分身跑完以后，下一单续最后结束的那一份会话，另一份列进记录（2026-10-11 主会话定，依据 `doc/goal.md`）。为什么：服务的规矩是任何活都不阻塞（O-1）；AI 能分身，这是有意偏离人类组织的地方。原 FR-3"并行分身共享记忆"由这条实现。验收：新写测试——专家在跑时再派一单，第二单的任务里带着专家的记录，跑完后两单都出现在这个专家名下。

**C-4 压缩晚、可配。** 每种后端的自动压缩阈值可以按角色配置，默认取该后端允许的最大值（Claude Code 的 `--autocompact`，pi 的压缩阈值）。验收：新写测试——配置的阈值出现在实际起进程的参数里。

**C-5 专家知道自己的原文在哪。** 每一单的提示里写明这个专家名下的原始记录在哪些文件，需要时它自己去读、去 grep。验收：新写测试——任务前缀里列出了记录路径，路径都存在。

**C-6 临时工率可度量。** 每一单在 `runs` 表里有自己的单号，开工时记一条装载事件（续上原会话、装载记录、全新对象），分母从这里算（2026-10-11 主会话定，依据 `doc/goal.md`）。`prd-check` 从台账算出：最近 N 单（默认 50，可配；"全新对象"一类只统计、不设目标，派活方要的不带上下文的分身（C-7）也算在这一类）里，派给已有专家却没带任何记录开工的单数（目标为 0），以及续上原会话、装载记录、全新对象三类的分布。为什么：持久性是否兑现要看数据，不看代码里有没有这个功能（10-01 评审：77% 的单子开的是新会话）。验收：`prd-check` 输出这组数字；派给已有专家的空白开工数为 0 才算 C-6 已实现。

**C-7 开分身带不带上下文，由组长选（2026-10-24「マスター」：「我其实想的是某种fork 带上下文和fork不带上下文的区别」）。** `seat_start` 带 `fork`，这一单就交给专家的分身而不是专家本人，专家忙不忙都一样；分身只跑这一单，跑完关闭，记录归入专家。`fork: "context"` 是 C-3 那种带着专家记录开工的分身。`fork: "fresh"` 是不带专家任何历史的新会话：不续会话，不给记录清单、交接、专长说明和未完成清单，提示里写明它是不带历史的新实例、只凭现场判断；它的会话永远不变成专家的会话，专家下一单仍续自己的；它的空白开工是派活方要的，C-6 把它算进"全新对象"，不算缺陷。对象上还没有专家时，照常新开专家（新专家本来就没有历史），回复里说明。不带 `fork` 时行为不变（交给专家本人，忙时自动开带上下文的分身）。做到一半被拦截后的接手（O-6）用的就是这个"不带历史的新会话"，同一套。为什么：证伪、复核、第二意见这类活，老专家的认知（它搭的环境、它的假设、它认为测到了的地方）正是要被怀疑的对象，带上下文等于自己审自己；之前只能换个目录骗出新专家，或者派天生一次性的 handyman（2026-10-24，DSR 的 R17–R19 验收）。验收：新写测试——`fork: "fresh"` 的那一单拿不到专家的会话、记录、交接、专长和未完成清单，跑完专家的会话不变、C-6 记为全新对象；`fork: "context"` 在专家空闲时也开出带记录的分身；`fork` 写错被拒；runner 在 fresh 模式下即使拿到会话文件也不续、不装载；场景 T-10。依赖：C-3、E-2。

### 4.3 专家的生命周期

**交接文档**固定四节：懂了什么、没做完什么、踩过的坑、原始记录路径（2026-10-11 主会话定，依据 `doc/goal.md`）。L-1、L-3、S-4 和 C-1 的兜底都用这个结构。

**L-1 合并。** `seat_merge {from, into, name?}`：续接 A 跑最后一单写交接文档；文档存进 B 的记录；A 归档，原因记"并入 B"；B 的下一单开工时任务最前面附这份交接和 A 的原始记录路径，只附一次。A 那一单失败时不归档 A，记一条事件。为什么：同一个对象散成几个专家时要能收回来；两段会话合不成一段，但交接文档能把 A 的理解交给 B，原文仍在磁盘上。验收：新写测试——合并后 A 已归档、B 的下一单前缀里有交接、再下一单没有。

**L-2 归档。** 关一个专家时记原因；正在跑的也记（现在跑着关会丢原因，`src/exec.mjs` 的 `closeSeatNow`）。归档的专家不在名录里，记录和台账都留着。验收：`tests/lifecycle.test.mjs` 加用例——跑着关、不跑时关，两种都有 `close` 事件带原因。

**L-3 拆分。** 一个专家的对象太宽时，拆成两个更窄的专家：续接原专家，按每个子对象各写一份聚焦的交接，交给两个新专家；原专家归档，原因记"拆为 X 和 Y"。为什么：粒度要细（第 3 节）；拆分的信号见 L-4。验收：新写测试——拆分后两个新专家的第一单前缀里各有自己那份交接。

**L-4 太宽的信号。** 一个专家的会话被压缩过、或会话长度超过该后端上下文的一半时，名录里标出"建议拆分"。为什么：拆不拆由组长定，但信号要由服务给。验收：新写测试——造一个超过阈值的会话，名录里出现提示。

**L-5 取消与超时（原 FR-12）。** 取消的是一单，不是专家：`task_cancel {seat, reason}` 取消这个专家正在跑的那一单，杀整棵进程树，记 `cancelled` 事件，专家回到空闲、不归档，这一单写到一半的会话日志算专家的记录。`seat_close` 只管归档（L-2）；关一个在跑的专家时先取消再归档，两条事件都带原因。每个角色有 `timeout_minutes`（默认 60），超时同样杀树，记 `timeout`（2026-10-11 主会话定，依据 `doc/goal.md`）。为什么：人类组织里叫停一件活不等于开除负责的人；原来 `seat_close` 一个入口两用，取消一单就把整个专家归档了。一个座位同一时刻最多跑一单（分身是另一个座位），所以先用座位号指那一单；`runs` 表有了单号以后也能按单号取消。验收：`tests/lifecycle.test.mjs` 现有超时用例；新写测试——取消后专家仍在名录、下一单续得上；跑着关有 `cancelled` 和 `close` 两条事件。

### 4.4 专家的行为

**B-1 先问自己知不知道。** 角色合同不规定专家每一单都必须走的作业流程。专家的第一步是判断：知道，就直接答，说明出自哪次、原文在哪；知道但可能过时（价格、版本、额度），答时标查证日期；不知道才去查。为什么："它就知道，你问它，一问一答就没了"（2026-10-10「マスター」）；现在 `roles/web_researcher.md` 写着"每次都按这个顺序"先搜 Hwiki 再上网，这是临时工的作业流程。验收：新写测试——同一领域专家连问两次同一个问题，第二次不发起任何联网或 Hwiki 调用，回答里注明出自上一单。

**B-2 写回 Hwiki（原 FR-1 中 web_researcher 的部分）。** 信息专家查到新东西，写回 Hwiki 自己的主题分区，标 AI 生成；"写入的目标就是搜索的目标"。验收：现有 web_researcher 合同与 `hwiki ai-note` 的提交记录；新写测试检查一次联网查询之后有对应的 ai-note 提交。

**B-3 跨角色靠问。** 记忆按"角色 × 对象"各存一份；一个专家需要另一个角色在同一对象上的理解时，可以读它的交接文档，或经组长问它。为什么：窄分布才收敛；原 REQUIREMENTS 7.2 的"岗位之间对话"在这里落地为"读对方的交接、经组长问"，不开放专家之间直接派活。"经组长问"就是组长点名派一单给对方专家（2026-10-11 主会话定，依据 `doc/goal.md`）。验收：新写测试——同一目录的 explorer 有交接文档时，coder 的任务前缀里列出它的路径；"经组长问"的验收照 E-2。

### 4.5 学习

**S-1 困难账本（原 FR-21）。** 困难由 runner 从痕迹识别，不问模型；按"角色 × 类型 × 工具"归类；组长和「マスター」裁决去向（合同、派活经验、服务、工具或项目、接受）；角色本职不算困难（`expected_traces`）。另外每条困难记下它属于哪个专家。验收：`tests/skill-loop.test.mjs`、`tests/expected-traces.test.mjs` 现有用例；新写测试——困难记录里有专家座位号。

**S-2 skill 循环照常运行。** 一个角色攒满 5 条新困难，服务派 refiner 写这个角色 skill 的候选版本，不启用，等审核。`skill_loop: false` 的角色（现在是 handyman 和 leader）不走：杂活的教训只能用一次（2026-10-10「マスター」）。2026-10-10「マスター」明确：持久性没立住时也不停这个循环。验收：`tests/skill-loop.test.mjs` 现有用例。

**S-3 审核门。** 候选版本由组长逐条把依据的困难判成真、不成立、偶发，再启用或退回；只有启用才写进 HSkills。理由：skill 是假设，经验要过审核门才变成规则（skill-refinement："The review gate is the point."）。验收：`tests/skill-loop.test.mjs` 的 enable / reject 用例。

**S-4 两层 skill。** 角色级 skill 记手艺（怎么写代码、怎么查资料），留在 HSkills；某个对象特有的坑记进那个专家的交接文档。验收：新写测试——refiner 的候选只改角色级 skill；L-1、L-3 产生的交接文档里有"坑"一节。

**S-5 角色记忆（原 FR-7）。** 角色级的少量事实，经 `memory_write` 写入、派活前注入；只能加事实，不能改职责；有大小上限。验收：现有记忆读写与注入用例。

### 4.6 派活与回报

**O-1 派活永远不阻塞（原 FR-4）。** 只有一种派活形态：交出任务后立刻拿到座位号，结果落进台账。验收：现有用例；派活入口（seat_start）永不阻塞；阻塞等待仅保留在独立取结果兜底工具 task_wait 与后台 CLI wait（见 O-2、O-5）。

**O-2 完成后叫醒组长（原 FR-5）。** 服务提供与宿主无关的完成信号：后台 `wait` 命令和可长轮询的事件端点。每个宿主按自己的能力接：有完成通知集成的由宿主通知，能跑后台命令的用 `wait`，能往会话里注入消息的由它的看护件注入（DSR 的 `followup` / `inject` 是一例，见 REQUIREMENTS FR-5 的机制说明）。验收：服务侧 `wait` 与事件端点的现有用例；每接入一个宿主，补一个该宿主侧的集成测试——派一单不去查，组长自己被叫醒。

2026-10-18「マスター」授权接入 Codex Desktop：完成通知绑定实际派活的聊天和运行号，由本机看护件等待服务事件，在一单进入终态后通过桌面宿主已有的会话接口叫醒原聊天，不依赖原生 subagent 或模型定时查询。普通输出事件不能冒充完成；重复事件不能重复叫醒；成功、失败、取消都应有最终回报。桌面接口不可用或拒绝调用时明确报告未送达，不绕过宿主的身份、授权或信任检查。验收包含发起聊天绑定、重复事件去重、桌面断连的聚焦用例，以及一次派活后不查状态、原聊天收到完成通知的真实验证。

**O-3 并发上限（原 FR-6）。** 同时最多 10 单，超了直接拒并说明当前数。验收：现有用例。

**O-4 有界报告（原 FR-14）。** 每单的最终报告落进 `.data/reports/`，取结果时默认只回有界的一段，超了给全文路径；报告记字节数和哈希。验收：现有报告用例；新写测试检查字节数和哈希字段。

**O-5 取结果（原 `task_result` / `task_wait`）。** 取一单的状态、用量、验收、未完成清单和报告，不吐原始事件流。未完成清单只新增本单原始用户任务要求但确实未完成的事项；岗位职责、服务给出的记录路径、未要求或明确禁止的动作不能自行变成待办。历史清单不是新任务，不自动执行；以前真正未完成的工作不因无关任务被清空，只有已完成或有证据表明原本不在授权范围才移除，无法确认的保留。收尾失败或结果不可用时仍保留原清单。2026-10-11「マスター」针对真实连通性与暗号续接测试要求“修”，据此明确范围。验收：现有用例及 T-9。

**O-6 做到一半被拦截时，换一个不带历史的新会话接着做（2026-10-24「マスター」同意修收场、不换掉 Sonnet）。** 后端模型的安全过滤在这一单已经调用过工具之后停下它（Claude Code 报 `model_refusal_no_fallback` 一类的系统事件）时，服务：（a）在结果里列出这一单改动过的文件：路径相对工作目录，git 仓库里附增删行数（相对开工时的 HEAD，开工前就脏的文件标出来），不是 git 仓库时按修改时间列；（b）自动接手一次：换一个不带这个座位历史的新会话（C-7 的 fresh），优先同岗位的 Codex 后端，Codex 起不来就用不带历史的 Claude 新会话；交给它原 brief（不带服务附在前面的记录、交接和未完成清单）、已改文件清单，以及"从现场接着做，先读这些文件的当前内容，不要重做已完成的部分"。接手那一单的结果作为原来这一单的结果交回，报告开头写明被拦和接手、列出改动清单；事件里记一条 `takeover`。只接手一次：接手的会话动过手之后也失败（包括又被拦），这一单就停下，照（a）报告到那时为止的改动清单。座位仍续原来的会话（接手的会话不带专家的历史，续它等于把专家清空），下一单按 C-2 被告知目录里变了什么。开工即被拦（还没调用工具）不算这一条：照旧换下一个后端从头做，并按 C-1 装载记录。别的"干到一半失败"（断线、额度）不接手，但结果里同样列出改动清单。为什么：2026-10-24 DSR 主会话派出的三单 coder 在一分钟内都被拦在半路（seat-coder-18 和它的两个分身，各调用过 10 到 26 次工具），一个文件停在函数中间、语法不通，组长只能自己接手；10-22 以前 Sonnet 5.5 约 39 单零拦截，10-23/24 两天 79 单里 5 单。触发源可能是当时的分类器，也可能是共享给分身的会话历史，数据分不清，不带历史的新会话两种都兜得住。验收：新写测试（假 Claude 在调用过工具之后报拦截）——结果里有改动文件清单和行数；自动起了一单不带历史的接手并交回它的结果、记了 `takeover` 事件；Codex 起不来时改由不带历史的 Claude 新会话接手；接手也失败或又被拦时停下并报告清单；开工即拦照旧换后端；其他半路失败的结果里也有清单；场景 T-10。依赖：C-7、C-2。

### 4.7 角色与边界

**R-1 角色是数据（原 FR-1）。** 角色的合同、工具白名单、后端顺序都写在 `roles.json` 和 `roles/<角色>.md`，换模型、改工具面只改数据。现有八个角色：explorer、web_researcher、coder、tester、handyman、librarian、refiner，以及 lead（R-6，2026-10-21）。验收：启动闸。

2026-10-21「マスター」要求接入 Antigravity CLI（`agy`）作为第五家订阅后端，排在 DeepSeek 前面：谷歌 2026-06-18 起不再让 Gemini CLI 服务 Google AI Pro / Ultra，这一档订阅只能经 `agy` 用（它还带 Claude Opus / Sonnet 5.5，用的是谷歌那份额度）。和另外三家同一套规矩：订阅登录、按会话 id 续接、续不上按 C-1 装载、动手前失败才换下一家；提示走 stdin，不上命令行。`agy` 没有只读开关（`--mode plan` 会停在等审批），只读岗位在它上面靠合同约束，不靠沙箱，README 写明这一点。已经存下的 `.data/presets.json` 里 `order` 缺这一家时，服务把它插在 DeepSeek 前面，不因此丢掉整份设置。验收：presets、会话识别、参数拼装的聚焦用例，以及一单真实派活和一单续接。

**R-2 合同版本化（原 FR-15）。** 合同配 `.VERSION`，与 `roles.json` 的 `contract_version` 不一致就拒绝启动。验收：现有启动闸用例。

**R-3 边界的启动期断言（原 FR-16）。** `grant` 与工具白名单恰好相等，`deny_intent` 不越界，`expert_by`、`skill_loop`、`expected_traces`、`backend_notes` 写错就拒绝启动。验收：现有启动闸用例。

**R-4 写入边界（原 FR-17）。** 专家的 `edit` / `write` 只能落在它自己的工作目录里，由代码检查。验收：现有用例。

**R-5 coder 只干定死的活。** 改法由组长定死，coder 照做；需要调查或判断的部分先派 explorer 出图（`dispatch/coder.md`，2026-10-10「マスター」）。验收：组长手册与 coder 调用指南里有这条；`prd-check` 检查这两处文字存在。

**R-6 Lead：能派组员、不能派 Lead 的岗位（2026-10-21「マスター」）。** 有一个岗位 `leader`（墙上叫 Leader，原名 `lead`）：派活方只给它需求和验收标准，它自己拆活、派给组员（其余岗位）、核结果、交回带证据的报告。为什么：DSR 这类宿主里的模型只当甲方，组长的活（拆、定改法、验收）交给更强的订阅 CLI。名字叫"组长"不叫"承包商""外包公司"：名字会把那个词背后的行为一起带进来，要的是对结果负责、自己定怎么做、需求不对就提异议。
- **执行器只用三家**：Claude Code、Codex、Antigravity，按这个顺序顺延，不落到 Grok 和 DeepSeek（`roles.json` 的 `backends`）。
- **工具是全的，自己做还是派由它判断**（2026-10-22「マスター」）：读、写、跑命令加派单，和 coder 一样再多一个 `dispatch`。自己做还是派出去按总成本判断，写在合同里，不用禁令替它做死：只给读工具的第一版，在 Codex 上读不了文件（Codex 读文件靠命令），为读一个文件多派了一单 tester。座位是被调用的，每一单都交回给发起它的派活方验收，风险由验收和各家沙箱兜住，不靠削工具。
- **只有一层**：只有 grant 里有 `dispatch` 的岗位能派单，而且只能派给 grant 里没有 `dispatch` 的岗位——Lead 不能派 Lead，组员不能派任何人，所以不会层层外包、不会循环。由服务端检查，不靠合同里的一句话。
- **派单人由服务认定**：每个座位的进程都带着自己的座位号（`SPECIALIST_CALLER_SEAT`），座位里起的 MCP 桥把它随派单一起交给服务；服务按座位号查岗位，记下这一单的 parent。请求里自己声称的不算。
- **座位里只看见该看见的工具**：Lead 座位的 MCP 只列派单、等结果、取结果、看座位、记验收这几个；组员座位一个都不列；宿主（不在座位里）照旧是全部。
- **MCP 只给 Lead 开**：Claude 用 `--mcp-config` 只挂这一个服务，Codex 用 `-c mcp_servers` 只挂这一个；Antigravity 读用户全局的 MCP 配置，所以靠上面两条拦住组员。
- 已知的缝：有 shell 的座位可以绕过 MCP 直接请求服务的 HTTP 端口，服务分不出来；这条缝在 R-6 之前就存在。Lead 有了 shell 之后它对 Lead 同样存在，"只有一层"对一个存心绕路的 Lead 就只剩合同在管（合同写明派活只走派单工具）。不补：没有注入时模型没有理由去绕，这和别的岗位靠合同守边界是同一个标准；要由服务强制，得给每个座位和每个宿主都发凭证，代价不值（2026-10-22）。
验收：新写测试——Lead 座位派组员成功并记下 parent；Lead 派 Lead、组员派任何人都被拒；座位里的 MCP 桥按岗位列工具；presets 按 `backends` 只排这三家；启动闸认 `dispatch`。外加一次真实派活：Lead 收到需求，派一个组员，交回带证据的报告。

**R-7 按后端追加的岗位说明（2026-10-24「マスター」）。** roles.json 里一个岗位可以写 `backend_notes`：键是后端（codex / grok / claude / antigravity / deepseek），值是一段非空文字。这一单落在哪个后端，就只把那个后端的说明拼进提示，新会话和续接都带；别的后端看不到。为什么：某个后端独有的能力（例如 Antigravity 自带的 Google 搜索 search_web）只该告诉跑在它上面的座位，写进通用合同会让其他后端读一句与它无关的话，模型也不一定知道自己跑在哪个后端。写错（不是对象、键不是已知后端、值不是非空字符串）启动闸拒绝。验收：启动闸用例；拼装用例（落在 antigravity 时提示里有、落在别的后端时没有，新会话与续接都覆盖）。

### 4.8 台账

**G-2 启动时核对进程（原 FR-9）。** 启动时核对"在跑"的单子，进程不在了标 `interrupted`，还活着就接管并补做收尾。验收：现有 adopt 用例。

### 4.9 跨宿主

**H-1 单一入口（原 FR-10）。** 任何宿主都只经本服务的 MCP 派活；宿主自带的旧派活工具撤掉（已知的一处：DSR 插件的 `call_subagent` 等，撤后只留看护件和提示词）。验收：每个已接入宿主一条检查，确认它的配置里没有第二个派活入口（新写，按宿主逐一列）。

### 4.10 后台角色

**K-1 图书馆管理员与代为提交（原 FR-18）。** 验收：现有用例与 Hwiki 的提交记录。

**K-4 管图书馆的角色负责机器之间的同步（2026-11-01）。** 写笔记的只在本地存；`roles.json` 里标了 `sync_remote` 的角色（librarian），服务在它开工前拉取并合并上游分支，让它的变化清单里也有别的机器写的笔记；在它的提交之后再拉一次、合并、推送。仓库允不允许 agent 推送看仓库自己的 `git config --local claude.allowPush`，不是 `true` 就什么都不做。开工前合并有冲突、而且冲突都在它自己的目录里：撤回合并，把每篇冲突的样子放进它目录下的 `.conflicts/`，在任务前告诉它先按语义合好；它结束后服务再并入同一批远端提交，冲突的几篇以它写的为准，提交并推送。它没改到的冲突文件不合、不推，下一单再交给它。冲突碰到它目录以外的文件，整次撤回、不推送，事件里写明。提交后那次合并碰上冲突（两台几乎同时整理）也只撤回，下一单开工时会再交给它。「マスター」：「这个冲突很多时候只需要判别一下语义就行了。你有这个智力干」，所以不另设主从：谁先碰上冲突谁合，合完推上去，另一台拉下来就没有冲突了。起因：Hwiki 的 Windows 和 Linux 两份从 10-25 分叉到 11-01（本地 31 个提交、远端 46 个），期间两边查 Hwiki 都看不到对方的笔记。「マスター」：「一个人 如果“存”图书馆的时候都得思考里面有什么新的。这很啥也很无用。这个就是图书馆管理员的工作」。验收：临时仓库实测（拉合推、冲突交给它合、它没合、目录外冲突、没开授权五种情况）；Hwiki 的提交记录。

**K-5 没有 shell 的角色也能挪笔记（2026-11-01）。** librarian 在自己目录根写挪动计划 `.moves.json`；它结束后服务把计划文件取出目录，交给仓库自己的挪动工具（`roles.json` 的 `move_plan.run`，在仓库根执行，Hwiki 是 `bin/hwiki ai-note-move --plan`），工具一次挪完并改 id、链接、目录页、在本地提交；失败就什么都不挪，计划原文记进事件，不进仓库。仓库外的旧路径引用失效是可接受的代价。起因：同一天 Hwiki 的鸿蒙笔记分在 `tech-practical/` 和 `harmonyos/` 两处，librarian 的合同不许动 id，没法归位。「マスター」：「改坏引用会怎么样？答案是不会怎么样。不如说修引用也是ta的工作」。验收：临时仓库实测（执行成功、执行失败两种情况）。

### 4.12 治理

**P-1 `node tools/prd-check.mjs`。** 先用假后端跑第 4.0 节的全部端到端场景，再逐条跑每条需求自己的验收（测试文件里用编号标注，例如测试名带 `[C-2]`、`[T-3]`）；一条需求只有自己的测试通过、且覆盖它的场景全部通过才算已实现。用人话打印：每个场景过没过、坏在哪一步；每条需求已实现或未实现、卡在哪；C-6 的真实数字；最近一次真模型场景验收的日期和结果。有任何一项未实现就以非 0 退出。另有 `--real` 开关，用便宜的真模型跑一遍全部场景并把结果存档。为什么：「マスター」不逐条验收，"做完"不能靠自述，也不能靠零件测试全绿。验收：它自己的测试——让一个场景故意失败，它覆盖的需求全部显示未实现；删掉一条需求的测试，那条显示未实现。

**P-2 入口指向 PRD。** README、`doc/connect.md`、`dispatch/team-leader.md` 开头都写明需求以 `doc/PRD.md` 为准；`doc/REQUIREMENTS.md` 开头写明已被取代。验收：`prd-check` 检查这四处文字。

**P-3 测试标注需求编号。** 每个验收测试在名字里带需求编号；没有编号的新测试不算任何需求的验收。验收：`prd-check` 列出没有对应测试的需求。

## 6. 实施顺序
