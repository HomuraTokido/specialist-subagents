# 实施改法（组长定，coder 照做）

2026-10-11 起草，配合 `doc/goal.md` 使用。这里写每一期的改法；需求本身以 `doc/PRD.md` 为准，两者冲突时改这份。

## 共同约定

- **"一单"和"专家"分开。** 专家仍是 `seats` 表的一行（座位号是键）；一单是 `runs` 表的一行（第 3 期加）。分身也是 `seats` 的一行，`parent` 指向专家，`fork = 1`，不进名录。
- **新工具的名字**（场景测试的 driver 已按这些名字写）：
  - `seat_start` 加可选的 `seat`（点名，E-2）。
  - `seat_rename {seat, name}`（E-5）。
  - `seat_merge {from, into, name?}`（L-1）。
  - `seat_split {seat, parts: [{name, topic?, cwd?}]}`（L-3）。
  - `task_cancel {seat, reason}`（L-5）。
  - 换后端用现有的 `POST /backend {mode}`，不加新入口。
- 测试名带需求编号，例如 `[E-5] …`。现有用例的期望要改时，改期望并在 commit message 里说明为什么。
- 台账迁移（G-3）：改表结构前把台账文件复制成 `ledger.sqlite3.bak-<时间>`；每个迁移都有回退测试：在旧结构的台账上跑新代码，旧记录一条不丢；回退到旧结构（删掉新加的列或表）后，旧代码还能读。

## 第 2 期：寻址

- **E-5 改名**：`store.renameSeat({seat, name})`。名字去掉首尾空白后不能为空，最长 80 字；不能和另一个活着的专家重名（E-1）；归档的专家不能改。改名记 `rename` 事件，正文写"原名 → 新名"。daemon 加 `POST /seat/rename`，MCP 加 `seat_rename`。
- **E-1 语义名**：
  - 新开专家的初始名，目录角色是 `<角色> · <目录最后一级>`，领域角色是 `<角色> · <领域>`，不含座位号。
  - 同一个对象已经有活着的专家时不再开第二个（忙时开分身，见 C-3），所以不再出现 `#2` 后缀。
  - 改名时拒绝和活着的专家重名。
- **E-2 点名**：`seat_start` 带 `seat` 时，跳过自动挑选，交给这个座位，用 `store.claimNamedSeat({seat, role, owner, parent})`。以下情况拒绝，消息写清原因和下一步：
  - 座位不存在。
  - 角色对不上。
  - 已归档：写明归档原因，"并入 X" 时指向 X。
  - 带的 `cwd` 或 `domain` 和专家的对象不一致。
  - 专家正忙：开分身（C-3，第 3 期）。第 2 期先拒绝并说"正忙"，第 3 期改成开分身。
  - 点名的专家要续会话、带记录，和自动挑中的一样。
- **E-3 说清挑了谁**：回复的 `note` 写清：
  - 交给了谁（名字和座位号）。
  - 它来过几次（这个专家名下已完成的单数）。
  - 为什么是它：点名、同一目录、同一领域、新开，或者是分身。
- **E-7 路径归一**：`dirKey` 先 `fs.realpathSync.native`（解开符号链接和 junction，失败就退回 `path.resolve`），再只在 win32 和 darwin 上转小写。新开专家存规范化后的真实路径。
- **E-6 名录**：
  - `seat_list` 每行写：名字、座位号、角色、对象、状态、来过几次、未完成条数、专长。
  - 加 `role` 过滤。
  - 分身不进名录。
  - 默认视图里不会有两个活着的专家同名。

## 第 3 期：连续性

- **runs 表**：`runs(id INTEGER PRIMARY KEY, seat TEXT, expert TEXT, task_seq INTEGER, started_at, ended_at, state, backend, load TEXT, had_records INTEGER, session_file TEXT, report_file TEXT)`。
  - `expert` 是分身的 `parent`，否则就是 `seat`。
  - `load` 取 `resumed`、`loaded` 或 `fresh`。
  - 开工时写一行，同时记一条 `load` 事件；收尾时补 `ended_at`、`state`、`session_file` 和 `report_file`。
  - `prd-check` 的 `c6Numbers` 读这张表（`id`、`seat`、`started_at`、`load`、`had_records` 这几列的名字和含义不变）。
- **C-2**：删掉"改动超过 20 个文件或 500 行就换新会话"的规则（`BIG_CHANGE_*`），一律续上原会话，附上变化说明；文件清单太长时照旧写进文件。
- **C-5 记录在哪**：每一单的任务前面加一段"你的记录"：
  - 这个专家名下最近 10 单的会话日志路径、报告路径，以及交接文档路径。
  - 只列存在的文件，并说明"需要时自己读或 grep"。
  - 段落开头固定写 `服务提示：你的原始记录`。
- **C-1 装载**：cli-runner 在续不上会话时（上一段会话是别的后端写的），不再只给路径：
  - 把上一段会话日志转成纯文本对话（codex rollout、claude jsonl、pi jsonl 都抽出用户和助手的文字），作为"你之前的对话记录"放在任务前面。
  - 超过 60000 字时，换成交接文档（没有就先只给路径）加原文路径。
  - 装载方式写进结果文件的 `load` 字段，再进 runs 表。
- **C-3 分身**：专家正忙时，再派给它的一单开分身：
  - `openSeat({…, parent: 专家, fork: 1})`，名字写 `<专家名>（分身）`。
  - 分身带着专家的记录开工：pi 会话就复制一份会话文件来续；其他后端按 C-1 装载专家最近的会话日志；C-5 的记录清单照列。
  - 收尾时，分身的会话日志和报告记进 runs 表、算在专家名下；分身座位关掉，关闭原因写"分身跑完"。
  - 专家的 `session_file` 改成最后结束的那一份会话（第 7 节第 1 条）。
- **C-4 压缩阈值**：`roles.json` 每个角色可以写 `compact: {<后端>: 数值}`；没写就用 presets 里各后端的默认（该后端允许的最大值）。cli-runner 把它变成该后端实际的参数，具体参数名以调研结果为准，查不到的不编。
- **C-6**：`prd-check` 读 runs 表。测试在一个样例台账上验算法。
- **输出成批写台账**：`makeTail` 每次 `drain` 读到的行，放进同一个事务里写（`store.inTransaction(fn)`）。原因是 2026-10-11 Windows CI 上一单打出 3000 行，每行一次提交，daemon 的事件循环被卡住十几秒；恢复时 keep-alive 连接被重置，客户端收到 `ECONNRESET`，日志里有证据。台账照旧逐行一条事件，只是提交次数变少。

## 第 4 期：生命周期

- **L-5 task_cancel**：
  - `exec.cancelRunNow({seat, reason})`：杀进程树，记 `cancelled` 事件，专家回到 `done`。若在跑的是分身，就关掉分身座位。
  - 被取消的这一单的会话文件照常记进专家的记录（结果文件里有就写）。
  - `seat_close` 关在跑的专家：先 `cancelRunNow`，再 `closeSeat`，两条事件都带原因（L-2）。
- **L-2**：`closeSeat` 总是记 `close` 事件，没给原因时写"未说明原因"。
- **交接文档**：写在 `.data/handoffs/<seat>/<时间>.md`，固定四节：懂了什么、没做完什么、踩过的坑、原始记录路径。
  - 由服务续接专家的会话，发一条 `（服务消息，不是新任务）写交接：……` 让它写，正文取它的回答。
  - 什么时候写（C-1）：会话快超过上下文的一半时、换后端之前、合并或拆分时。
- **L-1 合并**：`seat_merge {from: A, into: B, name?}`：
  1. 续接 A，让它写交接。
  2. 交接存进 B 的记录。
  3. A 归档，原因写"并入 B"。
  4. B 记一条"待附交接"。B 的下一单开工时，任务最前面附交接正文和 A 的原始记录路径，附完就清掉标记，只附一次。
  - A 写交接那一单失败：不归档 A，记一条 `merge` 事件说明失败原因。
  - 两人角色要相同。
  - 给了 `name` 就同时把 B 改成这个名字。
- **L-3 拆分**：`seat_split {seat, parts}`：
  1. 续接原专家，对每个子对象各写一份聚焦的交接（写交接的提示里点名子对象）。
  2. 开出新专家，对象是 `目录 + 主题`（或者给的 `cwd`），各自"待附交接"。
  3. 原专家归档，原因写"拆为 X 和 Y"。
- **什么时候主动写交接（C-1 的节点）**：每单收尾后检查专家的会话。下面两个节点各只写一次，写过就在座位上记一条 `handoff` 事件，正文注明是哪个节点：
  - 会话文字第一次超过 60000 字（C-1 装载文字的预算）：之后换后端会被截断，截断时就靠这份交接。
  - 会话第一次超过上下文的一半（L-4）。
  写交接是专家自己的一单：owner 记 `handoff`，任务是服务消息 `写交接：……`，和其他单一样占并发名额。
- **拆分后的对象（第 7 节第 3 条）**：`seats` 加 `topic` 列，`seat_start` 加可选的 `topic`。按目录挑专家时：
  - 那个目录只有一个活着的专家：就是它，带不带 `topic` 都一样。
  - 有几个按 `topic` 分开的专家：`topic` 对得上的那个；没带 `topic`、或者对不上：拒绝，列出候选（名字、座位号、主题），让组长点名或带上 `topic`。
- **L-4 太宽的信号**：满足下列任一条时，名录那一行标"建议拆分"：
  - 会话文件里有压缩标记（按调研结果识别）。
  - 会话长度（按字符数除以 3 估 token）超过该后端上下文的一半；上下文长度写在 presets 的 `levels`。

## 第 5 期：行为与学习

- **B-1**：重写 `roles/web_researcher.md`：
  - 去掉"每次都按这个顺序"。
  - 第一步先判断自己知不知道：知道就直接答，注明出自哪次、原文在哪；可能过时的标查证日期；不知道才查 Hwiki 和网。
  - 写回 Hwiki 照旧。
  - 版本号加一，`.VERSION` 同步改。
  - 其他角色合同里有同类的固定流程的，一并检查。
- **B-2**：用临时 git 仓库假装 Hwiki，测"联网查询之后有对应的 ai-note 提交"。
- **B-3**：同一目录有其他角色专家的交接文档时，C-5 的记录段一并列出它们的路径，并注明是哪个角色写的。
- **S-1**：困难记录里本来就有 `seat`；分身的困难记在专家名下（多一列 `expert`）。测试断言这一列。
- **S-4**：
  - refiner 的候选只能改角色级 skill：服务检查候选文件只落在这个角色的 skill 目录。
  - 交接文档要有"坑"一节：测试断言 L-1、L-3 产生的交接里有这一节。
- **内容测试**：用 subagent 当真模型，测 B-1、R-5 的合同内容，记录进 `doc/content-tests/`。

## 第 6 期：跨宿主与岗位墙（服务侧）

- **H-3**：MCP 壳在 `initialize` 时记下 `clientInfo.name`（和版本）；`seat_start` 没给 `owner` 时，用这个宿主名当 `owner`。
- **H-4**：daemon 加 `GET /pool`，返回一行人话快照：`池：<角色> 在跑 n / 未关闭 m；…`；CLI 加 `pool` 命令，读不到服务时打印 `池：未知`。
- **O-2**：CLI 的 `wait` 命令要有测试（服务侧）。
- **W-1**：`/wall` 的每个角色带 `experts` 列表，每人写名字、对象、来过几次、最近一单和"建议拆分"标记；页面在角色卡里展开显示这份列表，视觉不改。
