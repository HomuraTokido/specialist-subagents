## 第 7 节的未定事项怎么处理

PRD 第 7 节里有几条压着范围内的需求。下面的做法由主会话定下（2026-10-11），「マスター」不逐条审。

- 照"先改 PRD 再改代码"：每一条先从第 7 节挪进第 4 节对应的需求，写明"2026-10-11 主会话定"。
- PR 正文列一节"这次定下的做法"：定了什么、改了哪些需求，方便「マスター」以后想推翻时知道改哪儿。

六个漏洞的补法（PRD 第 7 节的建议补法，第 2 条按下面改过）：

1. 分身跑完后，下一单续最后结束的那一份会话，另一份列进记录。
2. 交接只在会出事的节点写，不定期刷新：会话快超过该后端上下文的一半时（L-4 的阈值）、换后端之前、合并或拆分时。节点之后又干的几单不在交接里，靠交接里的原始记录路径补。
3. 对象允许写成"目录 + 主题"，主题可以不填；匹配不上就列候选让组长点名。
4. B-3 的"经组长问"：组长点名派一单给对方专家，验收照 E-2。
5. 加 `runs` 表，每一单开工时记一条装载事件，C-6 的分母从这里算。
6. 取消与归档分开，见下面第 1 期的说明。

另外几个开放问题：

- **交接文档的结构**：固定四节——懂了什么、没做完什么、踩过的坑、原始记录路径。S-4 要求的"坑"一节就是其中之一。
- **"对象"的命名**：领域名用 Hwiki 主题名（E-4 已是这样）；目录专家由服务起初始名，组长用 E-5 改语义名。
- **C-6 的 N**：默认 50，可配。"全新对象"一类只统计，不设目标。
- **E-7 的大小写**：只在不区分大小写的文件系统上把大小写不同的路径认作同一个；Linux 上 `/a/Foo` 和 `/a/foo` 可能真是两个目录。
- **改台账之前先备份**：任何迁移在动「マスター」的台账前先复制一份，并带回退。

## 按期交付

每一期的做法都一样：先改 PRD（如需要），再写或补测试，再实现；期末跑一遍 `prd-check`，单独 commit，输出贴进 PR 正文。

### 第 1 期：治理先行

1. **P-1 `tools/prd-check.mjs`**
   - 先用假后端跑 `tests/scenarios/` 下的全部端到端场景，再逐条跑需求自己的测试。需求和测试的对应关系从测试名里的 `[编号]` 读出来。
   - 一条需求只有在两样都满足时才算已实现：它自己的测试通过，覆盖它的场景全部通过。没有对应测试的需求算未实现。
   - 用人话打印：每个场景过没过、坏在哪一步；每条需求已实现还是未实现、卡在哪；C-6 的数字（算不出的写"算不出：<原因>"，不编数字）；最近一次真模型验收的日期和结果。上面"不在这次范围里的"几条，显示为"需要本机：<原因>"。
   - 有任何一项未实现就非 0 退出。
   - `--real` 开关：用便宜的真模型（presets 里的 `deepseek-flash`）跑全部场景，结果存档。在容器里只用假后端测它的存档逻辑。
   - 它自己的测试 `[P-1]`：让一个场景故意失败，它覆盖的需求全部显示未实现；删掉一条需求的测试，那条显示未实现。
2. **假后端的语义**：假后端只"知道"装进它上下文里的东西（续上的会话加任务前缀），并记下自己有没有发起联网或 Hwiki 调用；能设成慢。优先扩展 `tests/fakes/` 里已有的假后端。
3. **T-1 到 T-8 场景测试**，放在 `tests/scenarios/*.scenario.mjs`，只由 `prd-check` 跑，不进 CI 的 `tests/**/*.test.mjs`。（历史注：这是第 1 期起草时的旧写法；现行 CI 已单独执行 `node --test "tests/scenarios/*.scenario.mjs"`。）
   - 断言只看结果，不看内部走了哪个函数。
   - 所有对服务的调用都经过一层 `tests/scenarios/driver.mjs`。还不存在的入口在 driver 里暂定名字：`seat_rename`、`task_cancel`、`seat_merge {from, into, name?}`；换后端用现成的 `POST /backend`，不加新入口。后面几期实现时用同样的名字。
4. **P-3 编号标注**：给现有测试的名字标上需求编号。PRD 里写"现有用例"的需求，从严标注，对不上就不标。
5. **P-2 入口文字**：README、`SKILL.md`、`dispatch/team-leader.md` 开头写明需求以 `doc/PRD.md` 为准；`doc/REQUIREMENTS.md` 开头写明已被取代。`prd-check` 检查这四处文字。（历史注：这是第 1 期起草时的旧写法；现行 P-2 检查对象为 `README.md`、`doc/connect.md`、`dispatch/team-leader.md` 与 `doc/REQUIREMENTS.md`。）
6. **PRD 改动：取消与归档分开**（第 7 节第 6 条）
   - 背景：台账里没有"一单"这个实体，只有 `seats` 和 `events`；`src/exec.mjs` 的 `closeSeatNow` 杀进程后顺手 `closeSeat`，所以取消一单等于归档专家。
   - L-5 改成：`task_cancel {seat, reason}` 取消正在跑的一单，杀整棵进程树，记 `cancelled`，专家回到空闲、不归档，这一单写到一半的会话日志算专家的记录；`seat_close` 只管归档，关在跑的专家时先取消再归档，两条事件都带原因。
   - 一个座位同一时刻最多跑一单，分身是另一个座位（带 `parent`），所以先用座位号指那一单。第 3 期加 `runs` 表后，`task_cancel` 再加按单号取消。
   - 实现放在第 4 期。

## 规矩

- **做不到的先跳过（「マスター」2026-10-11）**：真卡住的，写进 PR 正文"做不到的"一节，接着做别的。
- **但不隐藏**：不给测试标 `test.skip`，不削断言，不改场景去迁就代码。做不到的需求在 `prd-check` 里照实显示未实现。
- 不删除、不暂停、不缩小 PRD 的任何一条需求。PRD 改动只限上面写明的几处。
- 遇到 PRD 没写、这份文件也没写的设计问题，用最保守的写法继续，写进 PR 正文"这次定下的做法"，不擅自扩大范围。
- 改法由组长定死（AGENTS.md）。这次组长就是执行 goal 的模型自己：每一期动手前先把改法想清楚、写进 commit message。
- 测试要能在 Windows 和 Linux 上都跑。
- commit 和 PR 里不写模型名。
